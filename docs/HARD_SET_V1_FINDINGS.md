## 구멍 3 — 금액 보강 각주가 **엉뚱한 문서의 정정 전** 값을 집는다 (`plan.py:1003 _postfix`)  ★제출 셋에도 있음

이게 이번에 나온 것 중 제일 고치기 쉽고, **유일하게 제출 셋(58문)에도 이미 들어가 있는** 문제다.

`_postfix`의 금액 보강은 근거 뭉치를 flatten한 뒤
`계약금액[^\n]{0,14}?(금액)` 으로 첫 미매칭 값을 뽑아 각주로 붙인다.
그런데 정정공시 본문은 이렇게 생겼다:

```
정정항목 | 정정전 | 정정후 | 2. 계약내역 중 계약금액(원) | 154,102,712,000 | 178,800,382,017
```

`계약금액` 바로 뒤 14자 안에 오는 건 **정정 전** 칸이다. 그래서 규칙적으로 옛 값을 집는다.
`CORRECTION_RULES`에 "'정 정 후' 값만 쓰라"를 넣어 HCX를 잡아놨는데,
그 뒤에 붙는 코드 보강이 정정 전 값을 도로 끌고 들어온다.

원문 대조로 확인한 3건 (전부 `정정전` 칸):

| 문항 | 각주가 붙인 값 | 실제 정체 | 출처 |
|---|---|---|---|
| T5-C-005 | 3,077,703,837,261 | 6차 정정의 **정정전** (정정후는 3,083,318,360,998) | `20250331802494` |
| T6-O-010 | 154,102,712,000 | **정정전** (정정후는 178,800,382,017) | `20230410800882` |
| **TR-NAME-001 (dev, 통과)** | 35,395,538,396 / 35,423,244,432 | 무관한 계약의 **정정전/정정후 쌍** | `20241111800001` |

TR-NAME-001이 특히 나쁘다. 답변은 인도네시아 경찰 계약 **198,437,328,900원**을 맞게 말해놓고,
바로 아래 "※ 근거 원문에 적힌 금액"으로 **전혀 다른 계약**의 354억/354억을 붙였다.
저 두 숫자는 답변이 인용한 근거(`20250711800172`)에 **없다** — 회수된 12건 중 다른 문서에서 왔다.

**여기서 결함이 둘이라는 게 드러난다.** 하나는 위에서 말한 칸 오인(정정전을 집음)이고,
다른 하나는 **문서 오인**이다. TR-NAME-001은 칸을 틀린 게 아니라 **문서를 틀렸다** —
정정전·정정후 **둘 다** 집었고 둘 다 무관한 계약의 값이다.
그래서 "정정후 칸을 집게 고친다"만으로는 TR-NAME-001이 **안 고쳐진다**. 여전히 35,423,244,432를,
여전히 남의 계약에서 인용한다.

뿌리는 `plan.py:1044` 다:

```python
full = context + " ".join((it.get("text") or "")
                          for r in results.values() for it in (r.get("items") or []))
```

회수된 모든 문서의 본문을 **한 덩어리로 이어붙인 뒤** 정규식을 돌린다.
그래서 매치가 어느 문서에서 나왔는지 알 방법이 코드에 없다.
칸 오인은 이 위에서 벌어지는 별개 증상이고, 문서 오인이 셋 다를 설명한다.

**제출 셋 영향**: dev 58문 중 **13문**의 답변에 이 각주가 붙어 있다
(T1-C-003, TR-NAME-001, T1-C-004, T3-C-002, T3-C-005, T5-C-003, T6-O-005, T4-O-010,
TR-COR-002, T4-O-013, T6-O-007, T4-O-016, T6-O-008).
**13문 다 채점은 통과한다** — accept_patterns가 본문에서 이미 맞아서 각주는 점수에 안 잡힌다.
하지만 사람이 읽으면 "근거 원문"이라고 명시된 숫자가 답과 다르다. 정성 평가에서 손해다.

고칠 방향(선우 판단). **위가 아래를 포함한다** — 위 두 개는 검증한 3건을 다 덮고,
맨 아래는 T5-C-005·T6-O-010만 덮고 TR-NAME-001은 못 덮는다:

- **문서 단위로 훑기** — `full` 로 뭉뚱그리지 말고 item 하나씩 정규식을 돌려,
  답변이 인용한 접수번호에서 나온 매치만 각주에 쓴다. 셋 다 고쳐진다.
- **근거가 2건 이상이면 아예 발화하지 않기** — 제일 작고 제일 안전하다.
  단건 회수(정정 없는 단순 질의)에서만 각주가 붙으므로 오인 자체가 불가능해진다.
  dev 13문 중 각주가 사라지는 문항이 생기지만, 13문 다 본문에서 이미 채점을 통과하므로 점수 영향 없음.
- (위 둘 중 하나를 한 뒤 덤으로) `정정전 | 정정후` 표에서 **뒤쪽** 값 집기 —
  이것만 단독으로 하면 TR-NAME-001은 그대로 남는다.

## 채점 관련 메모

`run_eval.py`는 `closed`를 `any(accept_patterns)`로, `open`을 **60% 커버리지**로 채점한다.
따라서 **open + accept_patterns 정확히 2개 = 둘 다 맞아야 통과**(1/2 = 0.5 < 0.6).
hard_v1의 "양 끝단" 문항 5개(T5-C-005/006/007/009, T6-O-011)가 이 성질을 쓴다.
일부러 그렇게 설계한 것이니 패턴 개수를 임의로 늘리면 난도가 사라진다.

T5-C-012는 최초 실행에서 내 accept_patterns가 좁아 오답 처리됐다(파이프라인 답은 옳았다).
`"찾을 수 없"` 등 4개를 추가해 고쳤고, 그래서 서버 실행 시점 3/10 → 재채점 4/10이다.
나머지 6건은 답변 전문을 다 읽고 **진짜 실패**임을 확인했다.

제안 중 **"문서 단위로 훑기"** 를 택했다. "근거 2건 이상이면 미발화"도 검토했는데,
각주 목적(근거에 있는데 답변이 빠뜨린 금액 되붙이기 — T6-O-005 가 이걸로 살았다)을
버리지 않고도 오인을 막을 수 있어서다. 셋을 겹쳐 걸었다.

1. **문서 오인** — `full` 뭉치기를 없애고 item 하나씩 훑는다.
2. **인용 제한** — 답변이 `(근거 N)` 으로 지목한 문서의 값만 쓴다. 인용이 없으면 각주를 안 붙인다.
   (출처를 말할 수 없는 값을 "근거 원문"이라 적는 게 결함의 뿌리라서. 인용 없는 답변에서
   각주가 사라지는 건 의도된 손실이다 — dev 12문 전부 각주 없이도 본문으로 통과함을 먼저 확인했다.)
3. **칸 오인** — 정정 표식이 있는 문서에서는 라벨 뒤 **구분자만 사이에 두고 연달아 붙은**
   금액 나열의 마지막(정정 후)을 쓴다.

**수리 중 하나 더 나왔다.** 3번을 처음에 "라벨 뒤 160자 안 마지막 금액"으로 잡았더니
TR-NAME-001 에서 `계약금액(원) 198,437,328,900 최근매출액(원) 2,220,751,868,438` 의
**최근매출액**(다른 항목)을 집었다. 원문 대조로 잡았고, 한글 라벨이 나오면 나열을 끊게 고쳤다.
경욱이 형이 검증한 3건(TR-NAME-001·T5-C-005·T6-O-010)을 실제 원문 형태 그대로
`agent/test_footnote.py` 픽스처로 박았다 — **픽스처를 원문보다 단순하게 만들면
테스트가 통과해도 버그가 산다**는 걸 이번에 배웠다.

검증: test_footnote 6케이스 + 기존 postfix 테스트 회귀 전부 통과, dev 58/58 유지(재측정).
