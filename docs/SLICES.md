## S1. /ready + 기동 시 사전 로딩 — Brief

**사용자 결과**: 평가 첫 질의가 콜드스타트 19초를 먹지 않는다. 운영자는 `/ready` 한 번으로 "받을 준비 완료"를 확인한다.

**범위**:
- `server/app/main.py` lifespan에서 `AGENT_MODE != "mock"`일 때 백그라운드 스레드로 `get_searcher()` 로드 + 카나리 검색 1회(예: "SK하이닉스 신규시설투자") 성공 시 ready 플래그 셋
- `GET /ready`: 준비 완료 → 200 `{"status":"ready"}` / 로딩 중 → 503 `{"status":"loading"}` / 로드·카나리 실패 → 503 `{"status":"error","detail":"<원인>"}`
- `/health`는 현행 유지 (즉시 200, 로딩과 무관)

**범위 밖**: HCX 워밍업·키 검증, 응답 캐싱, Docker, 질의셋.

**재사용 자산**: `server/app/search.py`의 `get_searcher()` (지연 import 구조 유지, `OMP_NUM_THREADS=1` 제거 금지).

**하드룰**: mock 모드에서 torch/faiss가 import되면 안 된다. `/answer` 스키마 불변. 로딩 중 `/answer`가 들어와도 죽지 말 것 — 같은 락으로 대기시켜 이중 로딩 방지 (`threading.Lock`).

**위험**: 백그라운드 로딩과 첫 요청의 경쟁 조건(이중 로딩 → 메모리 2배). 락 필수.

**완료 기준**:
1. `AGENT_MODE=baseline` 기동 → `/ready` 처음 503, 로드 완료 후 200 전환
2. `/ready` 200 이후 첫 `/answer` 응답 3초 미만
3. `AGENT_MODE=mock` 기동 → `/ready` 즉시 200, torch 미로딩 (프로세스 RSS로 확인)
4. `python3 evalset/run_eval.py` 11문 결과가 기존과 동일 (8/11, 근거 recall 0.8)

**품질 기준**: 로딩 실패 시 `/ready`가 원인을 노출. 로그에 로드 시작/완료/소요 시간 남김. 이중 로딩 없음.

**품질 기준**: 후보의 인용이 실제 파일에 존재해야 함 (Fable이 재-grep으로 검수).

## S4. 질의셋 36문 확장 (8대 평가기준 공략) — Brief

## S5. HCX-005 실연동 검증 — Brief

*2026-08-07 Fable 작성. 2026-08-08 분할: **S5a(키 불필요 — 아래 범위 중 클라이언트·프롬프트·폴백 구현과 무키 검증, 완료 기준 ①제외 ②④)** / **S5b(키 필요 — HCX 실호출, 18문 재채점, 완료 기준 ①③)**. S5a는 S6 완료 후 즉시 착수 가능, S5b는 사용자가 `.env`에 키를 넣는 순간 측정만 남도록 준비.*

**사용자 결과**: 진짜 LLM이 붙은 첫 응답. 폴백으로는 원리적으로 불가능했던 것들(거절·공격 방어·비교연산)이 실제로 되는지 최초 확인.

**범위**:
- `server/app/llm.py` 신규: HCX-005 클라이언트. 타임아웃(연결 5s/응답 30s), 재시도 1회(지수 backoff), 429/5xx 구분 처리. **HCX 실패 시 추출형 폴백으로 강등** (절대 규칙 3: 어떤 경우에도 200+5필드)

## S6. 4GB 다이어트 — Brief (S3 실측으로 발동 확정, 우선순위 전면 재설계)

*2026-08-07 Fable 작성. S3 실측: 사인은 FAISS가 아니라 **임베딩 모델 fp32 로딩 스파이크(651MB→3.4GB/1초, 기동 3.8초 OOM)**.*

**사용자 결과**: 평가 환경(2vCPU/4GB)에서 서버가 실제로 돈다. 이게 안 되면 나머지 전부가 무의미.

**범위** — 우선순위 순서 고정 (각 단계 후 4GB 컨테이너로 재실측, 어디까지 로딩이 진행되는지 로그로 확인하며 점진 진행):
1. **모델 로딩 스파이크 제거** (사인 확정된 1순위): `search_lib.py`가 device=cpu일 때 fp32를 강제 — (a) safetensors mmap/lazy 로딩(`low_cpu_mem_usage` 계열)으로 체크포인트 이중 버퍼링 제거, (b) bf16 on CPU 가부 검토(NCP x86_64 기준 — 로딩만 저정밀 후 upcast 옵션 포함), (c) 최후수단 int8 ONNX(PLAN 기존 트랙). **선행 확인: search_lib/search_patch가 `data/` 하위(명섭 산출물, 읽기 전용)인지 우리 코드인지** — data/ 하위면 원본 수정 금지, `server/` 쪽 래퍼에서 오버라이드로 해결
2. **FAISS SQ8 재양자화** (2.1GB→0.53GB): 인덱스는 명섭 산출물 — 재양자화 산출물은 `data/`가 아닌 `server/artifacts/`에 생성 (data/ 읽기 전용 룰). **재양자화 후 18문 recall 변화 측정 필수** — 하락하면 수치와 함께 갈등 보고
3. **chunk_meta.jsonl(3GB) → SQLite** lazy 조회: 정상상태 RSS 최대 항목 제거
4. **torch CPU 인덱스 핀** (`--index-url https://download.pytorch.org/whl/cpu`): 이미지 8.65GB→약 2GB, 빌드 57분 단축 (S3 관찰 반영 — 메모리와 별개지만 S7 배포 시간을 좌우)

**범위 밖**: NCP 배포, 코드 리팩토링(다이어트에 필요한 최소 변경만), 검색 품질 개선.

**재사용 자산**: `gongsi-agent-s3` 이미지(비교 기준 — CPU핀 재빌드 성공 시 삭제), S3의 측정 절차(docker stats 스트리밍·inspect·3회 재현), `.dockerignore`.

**하드룰**: `data/` 수정·삭제·이동 금지 (산출물은 별도 경로). 외부 다운로드 금지 — `HF_HUB_OFFLINE=1` 유지, 모델 변환도 로컬 캐시로만. 채점은 HTTP 경유(내부 함수 호출 금지).

**위험**: SQ8 recall 저하(측정으로 판단), CPU 아키텍처별 bf16 지원 차이(colima aarch64 ≠ NCP x86_64 — 양쪽 논리 분기 금지, 안전한 공통해 선택), 명섭 산출물과 정합성(재양자화 인덱스가 chunk_id 매핑과 어긋나면 안 됨).

**완료 기준**: ① 4GB 제약 컨테이너(`--memory-swap=4g` 포함)에서 `/ready` 200 ② 18문(S4 완료 시 36문) 채점 완주 ③ RSS 피크 <3.5GB(docker stats) ④ 통과율·recall이 다이어트 전(호스트 11/18) 대비 동일 이상 — 하락 시 원인·수치 명시 ⑤ 단계별 전/후 RSS를 LOG.md에 기록.

**품질 기준**: 각 단계가 독립 커밋 가능 단위(어느 단계가 얼마를 벌었는지 추적 가능). 실패한 시도도 수치와 함께 기록.
