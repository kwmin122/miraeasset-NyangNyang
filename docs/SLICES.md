## S1. /ready + 기동 시 사전 로딩 — Brief

**사용자 결과**: 평가 첫 질의가 콜드스타트 19초를 먹지 않는다. 운영자는 `/ready` 한 번으로 "받을 준비 완료"를 확인한다.

**범위**:
- `server/app/main.py` lifespan에서 `AGENT_MODE != "mock"`일 때 백그라운드 스레드로 `get_searcher()` 로드 + 카나리 검색 1회(예: "SK하이닉스 신규시설투자") 성공 시 ready 플래그 셋
- `GET /ready`: 준비 완료 → 200 `{"status":"ready"}` / 로딩 중 → 503 `{"status":"loading"}` / 로드·카나리 실패 → 503 `{"status":"error","detail":"<원인>"}`
- `/health`는 현행 유지 (즉시 200, 로딩과 무관)

**범위 밖**: HCX 워밍업·키 검증, 응답 캐싱, Docker, 질의셋.

**재사용 자산**: `server/app/search.py`의 `get_searcher()` (지연 import 구조 유지, `OMP_NUM_THREADS=1` 제거 금지).

**하드룰**: mock 모드에서 torch/faiss가 import되면 안 된다. `/answer` 스키마 불변. 로딩 중 `/answer`가 들어와도 죽지 말 것 — 같은 락으로 대기시켜 이중 로딩 방지 (`threading.Lock`).

**위험**: 백그라운드 로딩과 첫 요청의 경쟁 조건(이중 로딩 → 메모리 2배). 락 필수.

**완료 기준**:
1. `AGENT_MODE=baseline` 기동 → `/ready` 처음 503, 로드 완료 후 200 전환
2. `/ready` 200 이후 첫 `/answer` 응답 3초 미만
3. `AGENT_MODE=mock` 기동 → `/ready` 즉시 200, torch 미로딩 (프로세스 RSS로 확인)
4. `python3 evalset/run_eval.py` 11문 결과가 기존과 동일 (8/11, 근거 recall 0.8)

**품질 기준**: 로딩 실패 시 `/ready`가 원인을 노출. 로그에 로드 시작/완료/소요 시간 남김. 이중 로딩 없음.

## S2. 질의셋 유형 ④⑤⑥ 채워 12문 스모크 — Brief

**사용자 결과**: 6개 과제 유형 전부 ≥1문인 12문 스모크셋 — 선우가 전 유형에서 파이프라인을 테스트할 수 있다.

**범위** (Sonnet은 **후보 발굴까지만**, jsonl 추가는 Fable 확정 후):
- 부족 유형: ④비교·연산 Open, ⑤복합추론 Closed, ⑥복합추론 Open (현재 0문씩)
- 각 유형 후보 2~3개를 `data/corpus/` 원문에서 발굴, 후보마다 아래를 **최종 보고로 제출** (LOG.md 기록은 Fable이 검증 후 수행 — 병행 슬라이스와 파일 경쟁 방지, 이 슬라이스는 전 과정 읽기 전용):
  - 질문 초안 / 예상 골드 / rcept_no / **원문 XML 인용 2줄 이상** / 검증에 쓴 grep 명령
  - **혼동 가능 공시** (같은 회사 유사 건 — 예: SK하이닉스 M15X 4월 건 vs 7월 용인 건)
- 소재 리드: ⑤ 두산퓨얼셀 계약 체결→해지 추적 / ④ 자금조달 방식 비교(유상증자·CB·BW) / ⑥ 같은 회사 2023 vs 2025 사업보고서 비교
- 계산 문항은 계산 과정(피연산자 출처 rcept_no 포함)을 골드에 명시

**범위 밖**: `run_eval.py` 채점 로직 변경 (필요해 보이면 갈등 보고), 36문 확장, 서버 코드.

**하드룰**: 골드는 원문 인용 없이 제안 금지. 정정공시 있는 건은 최신본 기준. 코퍼스 밖 지식으로 골드 만들기 금지.

**완료 기준**: 유형 ④⑤⑥ 각 ≥2 후보가 인용·혼동공시 포함으로 **최종 보고로 제출됨** → Fable 검증 후 총 12문으로 `questions_v1.jsonl` 확정 → `run_eval.py` 12문 채점 완주. (baseline 통과율은 완료 기준 아님 — 추출형 폴백 한계)

**품질 기준**: 후보의 인용이 실제 파일에 존재해야 함 (Fable이 재-grep으로 검수).

## S3. Docker 2vCPU/4GB 실측 — Brief

**사용자 결과**: "평가 환경 스펙에서 실제로 돈다/안 돈다"를 숫자로 안다. (주최측이 이 스펙으로 시뮬레이션했다고 설명회에서 확인)

**범위**:
- `Dockerfile` (python:3.11-slim, `server/` 복사, requirements 설치. **`data/`는 굽지 말고 볼륨 마운트**)
- `docker run --cpus=2 --memory=4g -v $PWD/data:/app/data ...` 로 기동
- 측정해 LOG.md에 기록: 기동→`/ready` 200 시간, RSS 피크(`docker stats`), 11문 채점 p50/p95, OOM 여부

**범위 밖**: 다이어트 구현(SQ8/SQLite — 실패 시 갈등 보고만 하고 멈춤), NCP 배포, 이미지 크기 최적화.

**하드룰**: `.env`·키를 이미지에 넣지 말 것. `data/`를 이미지에 굽지 말 것.

**완료 기준**: 측정 리포트가 LOG.md에 기록됨. **실패도 완료다** — OOM이면 시점·RSS 곡선을 남기는 것이 산출물. 성공 기준: `/ready` 200 + 11문 완주 + RSS 피크 < 3.5GB.

**품질 기준**: macOS Docker Desktop은 VM이라 NCP 실측과 다를 수 있음을 리포트에 명시.

## S4~S8 개요 (착수 시 Fable이 Brief 작성)

- **S4 36문 확장**: 8대 평가기준(정확성·근거완전성·요구충족·할루시네이션·추론논리·안전성·정보한계 역질문·근거표시)을 각각 공략하는 문항 설계. 단위 함정(원/백만원), 연결/별도, multi-evidence, 최근 기간(2025~2026.03), 섹터 커버리지(방산 수주·반도체 CAPEX·바이오 임상·엔터 부문매출·금융 NIM/CSM). dev/blind 분리.
- **S5 HCX 실연동**: `.env`에 키 → baseline이 HCX-005 호출 → 12문 재채점, TR-LIM(역질문)·TR-ATK(공격) 통과가 핵심 관찰점. 키는 .env만, 절대 커밋·카톡 금지.
- **S6 다이어트(조건부)**: FAISS SQ8 재양자화(2.1GB→0.53GB), chunk_meta.jsonl→SQLite, 필요시 int8 ONNX. S3 리포트가 트리거.
- **S7 NCP 배포**: 서버 생성(2vCPU/4GB), Docker 배포, HTTP 공개, SSH는 본인 IP만. 방화벽·도메인은 주최측 공지 따름.
- **S8 리허설·프리즈**: 팀 통합 테스트(선우 에이전트 `sunwoo` 모드), 전 문항 실측, 9/6 프리즈 태그, 9/7~20 모니터링 체계(로그 확인 루틴), 9/30 전 리소스 삭제 체크리스트.
