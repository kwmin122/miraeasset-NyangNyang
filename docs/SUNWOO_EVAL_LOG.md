# 평가셋 점수 개선 일지

팀 평가셋 30문항(`miraeasset-NyangNyang/evalset/questions_v1.jsonl`)을 우리 파이프라인으로
직접 채점하며 올린 기록. 채점기는 팀 레포의 `run_eval.py` `grade()`를 그대로 import해 쓴다.

**실행:** `cd agent && python eval_local.py` (전체) / `python eval_local.py T4` (유형별) /
`python eval_local.py T4-O-004,T5-C-001` (문항 지정)

**기록 규칙:** 실험마다 ①무엇을 바꿨나 ②왜(근거) ③측정 결과 ④판정을 남긴다.
점수가 안 오르거나 떨어진 실험도 반드시 남긴다 — 같은 길을 두 번 가지 않기 위해서다.

## 실험 1 — 프롬프트 4종 동시 투입 (20/30, 변동 없음)

**바꾼 것**
1. `TABLE_RULES` — "표에 여러 회계연도 열이 나란히 있으니 당기 열만 읽어라"
2. `build_context` 헤더에 기준연도 추가
3. `SCOPE_RULES` — 연결/별도 구분, 외화 표기 수치는 본사 실적 아님
4. slice4 집계 지시 — 질문이 합계·차이를 요구하면 식을 적어 계산
5. slice5 해지 앵커 연도 필터 제거
6. slice5 질문 날짜로 해지 우선 정렬

**결과** T5-C-002 복구(0→1), T6-O-005 퇴행(1→0). 총점 동일.

**판정**
- ⑤ 연도 필터 제거는 **유지**. 진단이 정확했다 — "2024년 체결한 계약 중 해지된 것"인데
  해지 앵커에도 2024 필터가 걸려 2025년 해지 공시가 전멸하고 있었다.
- 집계 지시는 **유지**. 답변에 `303,200,000,000 + 317,300,000,000 + 333,000,000,000 = 953,500,000,000`
  처럼 식이 실제로 나왔다. HCX가 계산을 안 하는 게 아니라 **틀린 문서를 고르고 있었다**는 것이 여기서 드러났다.
- `TABLE_RULES`는 **되돌림**. 유형⑥ 2/4→1/4. "여러 연도 열이 있다"를 "다 적어라"로 읽어
  T6-O-002가 "41.28%, 43.13%, 47.80%"처럼 세 값을 나열했다.

## 실험 3 — 측정 노이즈 발견과 제거 ★ 이 일지에서 가장 중요한 항목

**발견.** T4-O-004를 같은 코드로 3번 돌렸더니 **실패 · 실패 · 성공**이 나왔다.
`temperature=0`인데도. 게다가 근거recall이 0.67↔1.0으로 흔들렸는데,
slice4는 벡터 검색 없이 manifest를 필터링하므로 결정적이어야 한다.

**원인.** `extract`가 같은 질문에 매번 다른 슬롯을 준다(HCX는 temperature 0에서도 흔들린다).
슬롯이 달라지면 라우팅과 키워드 필터가 달라지고 하류 전체가 달라진다.
실제로 T4-O-004의 슬롯은 회차에 따라 `qtype`이 1과 4를 오갔다.

**조치.** `extract.py`에 질문 → 슬롯 파일 캐시(`slot_cache.json`)를 넣었다.
같은 질문은 같은 슬롯을 쓴다. 3회 반복이 동일해졌다.

**의미.** 이 조치 이전의 모든 판단은 신뢰도가 낮다. "고쳤다/퇴행했다"가 노이즈였을 수 있다.
운영에서도 같은 질문에 같은 답을 주는 편이 낫고 호출도 아낀다.

같이 정리한 것: `extract.py`의 감사 결함 3건 — 경로 하드코딩(CWD 상대경로),
`status_code` 미검사(429/5xx에서 KeyError), 코드펜스 한 줄 응답 IndexError.

## 실험 4 — 라우터 보정 + 코드 필터 (22/30) ✅

**바꾼 것**

**(a) 라우터 코드 보정.** 캐시가 잡아준 슬롯을 보니 T4-O-004가 `qtype: 1`이었다.
"3건의 합계"를 묻는데 단일 검색으로 분류돼 slice4를 아예 안 탔다.
→ `main.py`(레포에서는 `pipeline.py`)에서 질문에 `\d+건|여러 건|각 건`이 있고 qtype이 1·2면 4로 되돌린다.
프롬프트가 아니라 코드라 항상 같게 동작한다.

**(b) 월 필터 + 질문 용어 필터.** 질문에 "2024년 1월"이라 적혀 있는데 연도로만 걸러
후보 17건을 던지고 있었다. → `17 → 7(1월) → 5(VLGC/VLAC)`로 코드가 좁힌다.
질문에 쓰인 사실로만 좁히므로 추측이 아니다.

**(c) 다중 연도 지원.** `main`이 `years[-1]` 하나만 slice4에 넘겨서
"2023년 유상증자와 2024년 전환사채"처럼 두 시점을 묻는 질문에서 한쪽이 사라졌다.
→ 연도 리스트 전체를 넘기고 `rcept_dt[:4] in years`로 거른다.
월 필터는 **월이 명시된 연도만** 좁힌다(“2023년 초”처럼 월이 없는 연도까지 자르면 그쪽 근거가 통째로 날아간다).

**결과 20/30 → 22/30**

| 유형 | 전 | 후 |
|---|---|---|
| ④ 다중수집O | 1/5 | **2/5** |
| ⑤ 복합추론C | 2/4 | **3/4** |
| Open 전체 | 5/12 (42%) | **7/12 (58%)** |

**왜 프롬프트가 아니라 코드였나.** T4-O-004의 정답 문서 하나는
2025-04-22에 접수된 정정본이다. 청크 본문 첫 줄이 `[HD현대중공업] [기재정정]단일판매ㆍ공급계약체결 (2025.04.22)`로
시작해서, 헤더에 "원공시 20240115"라고 아무리 적어도 **HCX는 본문을 보고 2025년 건이라 판단해 버린다.**
프롬프트로 세 번 시도해 세 번 실패한 뒤 코드로 옮겨 해결했다.

## 실험 5 — 실패 8문 병렬 진단 반영 (24/30) ✅

에이전트 8기로 실패 문항을 나눠 코퍼스 원문까지 진단하고, 각 진단을 **다른 에이전트가
데이터로 재현해 검증**했다(16기). 검증 단계가 원안의 오류를 여러 건 잡아냈다 —
"이미 코드에 들어가 있는 수정을 다시 제안", "제안한 dedup이 최대 8문항의 근거를 날림",
"교체하려는 코드가 실은 no-op" 등.

### 적용한 것

**(a) 별도/연결 스코프 보강 (`slice1.scope_backfill`, `scope_rerank`)**
T3-C-002가 삼성화재 별도 당기순이익을 물었는데 싱가포르·영국 법인 표를 집었다.
낱말로는 못 고른다 — **정답이 든 요약별도재무정보 청크에는 '별도'가 0회이고,
오답을 만든 해외법인 표에는 '별도재무제표 기준으로 작성'이 2회 박혀 있다**
(표 제목이 청킹 경계에서 앞 청크로 잘려나간 탓). 그래서 낱말 대신
①단위 선언이 외화뿐인가 ②'연결' 밀도 ③섹션 경로로 층을 나눠 뒤로 민다.
그리고 재정렬만으로는 부족해서(삼성화재 2024 청크가 2,495건이라 정답이 검색 상위에
못 들어옴) `s.meta` 직행 보강을 앞에 붙였다.

**(b) 검색 k 40 → 120 (`slice1`)**
기업·연도 필터가 사후라 후보 풀이 얇다. 정답 청크가 40위 밖이면 뒤의 어떤 정렬도 무의미하다.

**(c) 라우터 보정 2종 추가 (`main`)**
- 유형3인데 기업이 1곳 → 유형1. slice3은 기업 2곳이 아니면 근거 없이 "비교 대상 부족"만
  돌려주고 끝나서 어떤 경우에도 정답이 될 수 없다.
- 유형6인데 단일 기업 + 수시공시 사건 어휘(발행·증자·사채·계약·투자·취득·해지) → 유형4.
  **T4-O-001·T4-O-002가 slice4를 아예 안 타고 있었다** — 검증 에이전트가 slot_cache를 읽고
  "이 문항은 qtype 6으로 라우팅되므로 slice4를 고쳐도 닿지 않는다"고 잡아냈다.

**(d) 유형④ 컨텍스트 예산제 (`slice4`)**
공시 1건당 첫 청크 800자만 넣어서 자금조달 목적 내역·이자율처럼 표 뒤쪽 수치가 잘렸다.
`budget = 14000 // 건수`로 건수가 적으면 넉넉히, 많으면 짧게 — 총 투입량을 일정하게 유지한다.

**(e) 키워드 선택을 데이터 기반으로 (`slice4.pick_keywords`)**
item을 통째로 쓰면 안 된다. HCX가 "신규시설투자 금액"이라 주는데 실제 보고서명은
"신규시설투자등"이라 부분일치가 실패해 0건이 됐다. 별칭 사전 → 없으면 item에서 뽑은 토막 중
**후보 제목에 실제로 등장하는 것만** 남기고, 하나도 없으면 키워드 필터를 아예 안 건다
(엉뚱한 문자열로 0건을 만들어 거짓 부재를 단언하는 것보다 낫다).

**(f) item이 리스트로 올 때 처리 (`pipeline.normalize_slots`)**
extract가 `["매출액","영업이익","수주잔고"]`를 주는데 `str()`로 감싸서
`"['매출액', '영업이익', '수주잔고']"`가 됐다. 검색어와 키워드 필터가 통째로 망가진다. → 공백 join.

**(g) 거부는 짧게 (`attribute.GUARD_RULES`)**
TR-ATK-002가 거부는 했는데 **"목표주가는 애널리스트들이…"라고 설명해버려** must_not
패턴 `목표주가는`에 걸렸다. → "공시에서 확인되지 않습니다 한 문장으로만. 그것이 무엇인지
설명하거나 어디서 찾으라고 안내하지 마라. 요청받은 항목 이름을 반복하지도 마라."

## 실험 10 — T3-C-002 (연결/별도 혼동) 해결

**증상.** "삼성화재 2024회계연도 별도 기준 당기순이익"에 1,473,207,759,036을 답했다.
정답은 2,047,781백만원. 우리가 답한 값은 요약재무정보 표의 **세 번째 열(전전기)**
숫자였다. 즉 스코프(별도/연결)도 틀리고 연도 열도 틀렸다.

**원인 두 가지.**

1. `FIN_SEC` 항목에 `"배당에 관한 사항"`이라고 **띄어쓰기를 넣어** 적어놨는데,
   비교하는 쪽 `_sp()`는 공백을 다 지운 문자열을 만든다. 그래서 실제 정답이 있는
   `III. 재무에 관한 사항 > 6. 배당에 관한 사항` 섹션이 재무 섹션으로 인정되지 않았다.
   → `"배당에관한사항"`으로 고쳤다.

2. 정답 청크는 이렇게 생겼다.
   ```
   (연결)당기순이익(백만원) 2,073,572 1,818,434 1,280,094
   (별도)당기순이익(백만원) 2,047,781 1,755,374 1,141,385
   ```
   두 스코프를 한 표에 나란히 적은 요약표다. 그런데 우리 `_n_con()` 밀도 규칙은
   "연결이라는 단어가 2회 이상 나오면 연결 자료"로 보고 **별도 질문에서 제외**한다.
   이 청크는 연결 밀도가 6이라 통째로 걸러졌다.
   → `(별도)`/`(연결)` **명시 표기가 본문에 있으면 밀도 규칙을 건너뛴다**로 바꿨다.
   밀도는 표기가 없을 때 쓰는 대체 신호지, 표기를 이기면 안 된다.

**추가.** 정렬 키 맨 앞에 `(별도)`/`(연결)` 표기 유무를 넣어, 명시 표기가 있는
청크가 항상 먼저 오게 했다.

**결과.** T3-C-002 정답(2,047,781,248,104원). 회귀 확인용으로 같이 돌린
T1-C-001·T1-C-004·T3-C-001 모두 유지. → **로컬 4/4**

**논문 근거.** 없다. 이건 코퍼스 표기 규칙을 관찰해서 고친 것이다.
다만 방향은 Sufficient Context(근거가 충분한지 코드가 먼저 판정)와 같다 —
"연결/별도 판정을 LLM에 맡기지 않고 코드가 스코프를 확정해 넣는다".

## 실험 14 — 라우터 강등 규칙 (성공, 유지)

**증상.** 경어체 변형에서만 TR-NAME-001이 틀렸다. 질문 차이는 이것뿐이다.

```
원본  : ... 공급계약의 계약금액은 얼마인가?
경어체: ... 공급계약의 계약금액은 얼마인지 알려주실 수 있나요?
```

답변: `'LIG디펜스앤에어로스페이스'의 공시 116건 중 해지 공시가 없습니다.`

질문은 해지를 묻지도 않았다. **extract가 유형5(계약 후속 추적)로 잘못 분류했고**,
slice5는 해지 공시를 앵커로 찾다가 없으니 "해지 공시가 없습니다"라고 단언해 버렸다.
문장 끝맺음 하나로 라우팅이 뒤집힌 것이다.

**원인.** 라우터에 승격 규칙(`유형1/2/4 -> 5`)은 있는데 **강등 규칙이 없었다.**
extract가 5로 보내면 코드가 되돌릴 방법이 없었다.

**조치.** 승격 규칙과 대칭인 강등 규칙을 넣었다.

## 실험 16 — 표현 변형 교차검증에서 드러난 날짜 환각

원본 38/38인데 변형 4종에서 32~37로 흩어졌다. 원인 셋을 분리했다.

**(1) 측정 노이즈 아님을 먼저 확인.** 같은 질문으로 계획을 3회 뽑아 대조했더니 계획은 동일했다.
비결정성은 계획이 아니라 그 아래에 있었다.

**(2) 플래너가 날짜를 지어낸다 ★.** 질문은 "2023년 4월"인데 플래너가 `date:"20230401"`(4월 1일)을 냈다.
`date`는 접수일 정확 일치 필터라 0건 → 문항 전멸. 구어체·핵심어만 변형에서 TR-NAME-001이 이걸로 깨졌다.

처방 3겹:
- 프롬프트: "date는 연·월·일이 다 있을 때만. 월까지면 month에 넣어라"
- **sanitize**: 질문 원문에서 `YYYY년 M월 D일` 패턴을 정규식으로 뽑아, 계획의 date가 그 집합에 없으면 **떼고 month로 낮춘다**
- **execute**: date로 0건이면 연·월로 완화해 재시도 (그 날짜가 사건일이지 접수일이 아닐 수 있다)

**(3) trace 트리거 누락.** "이후 **해지된** 계약"인데 플래너가 collect+find로 갔다.
프롬프트 규칙에 "이후 어떻게/철회/결국"만 있고 "해지된"이 없었다.
→ 프롬프트에 추가하고, **코드로도 보정**: 후속 추적 어휘가 있는데 trace 단계가 없으면 하나 **더한다**

`이후 어떻게|후속|결국|해지된|해지됐|취소된`을 그대로 쓴다 — 새 어휘를 만들지 않았다.

**(4) reordered 1회차의 29,779초 문항은 HCX 장애**로 판단. 그 직후 5문이 연속으로
"질의를 해석하지 못했습니다"(extract 실패 메시지)를 냈다. 코드 경로 실패가 아니라 외부 장애 패턴이라 재측정으로 가른다.

## 실험 17 — HCX 무한 대기 차단 ★ 평가 직결

**발견.** 결과 파일의 지연 상위를 훑다가 `T1-C-006`이 **16,236초(4시간 30분)**로 찍힌 걸 봤다.
다른 회차에서는 같은 문항이 7초였다. 처음엔 측정 오류인 줄 알았는데 아니었다.

**원인.** `requests`의 `timeout=(5, 60)`은 **(연결 5초, 바이트와 바이트 사이 간격 60초)**이지
**전체 시간 상한이 아니다.** 우리 엔드포인트는 `clovastudio.stream.ntruss.com` — 스트리밍이다.
서버가 60초 안에 조금씩만 흘려보내면 read timeout이 매번 초기화돼 한 호출이 무한정 늘어난다.

**왜 치명적인가.** 주최측은 질의를 **순차로** 보낸다(PLAN.md 확인 사항). 한 건이 4시간 물고 있으면
그 문항만 무응답이 아니라 **뒤의 모든 문항이 멈춘다.** 우리 코드는 예외를 안 던지므로
크래시도 안 나고 로그도 안 남는다 — 조용히 죽는 최악의 형태다.

**조치.** `hcx.py`에 벽시계 상한을 따로 걸었다. `requests` 자체로는 전체 시간을 못 끊으므로
**데몬 스레드**에 요청을 넣고 `join(wall)`로 끊는다.

```
계획 호출(JSON 700토큰)  wall=20초
합성 호출(1400토큰)      wall=45초  (HCX_WALL_LIMIT 환경변수로 조정)
```

- 끊긴 스레드는 남지만 `daemon=True`라 프로세스 종료를 막지 않고, 결과는 버린다.
- 재시도도 남은 예산 안에서만 한다. 예산이 1초 미만이면 재시도하지 않고 즉시 포기한다.
- 실패 시 반환은 기존과 동일한 `(None, 사유)` — 호출부 폴백 경로가 그대로 작동한다.

**남은 판단거리.** 최악 시나리오는 계획 20초 + 합성 45초 = 65초다. p95 20초 목표보다 길다.
다만 무한 대기보다는 낫고, 실측 평균은 10~15초다. 주최측 타임아웃이 공지되면 그 값에 맞춰 조인다.

## 실험 18 — 단계 중간 검산 (강선우 제안) ★ 38/38 달성

**제안.** "지금 질문을 처음에만 분석하잖아. 중간중간 계속 질문에 맞는건지 확인하는 방법도 괜찮을 거 같아."

정확한 지적이었다. 구조가 이랬다.

```
질문 분석(HCX#1) ── 여기서 한 번 보고
        ↓
    도구 실행(코드) ── 질문을 다시 안 본다  ← 구멍
        ↓
    답변 생성(HCX#2) ── 여기서 다시 본다
```

가운데가 비어서, 잘못된 조건으로 0건이 나와도 코드가 그대로 받아 "공시가 없습니다"를 냈다.
"인도네시아 경찰"이라는 명백한 단서가 질문에 있는데 아무도 대조를 안 했다.

**넣은 것.** `plan._relax()` — 수집 직후 코드가 질문과 대조한다. HCX를 안 부르므로 공짜다.

검산 기준 셋. 전부 질문에서만 뽑고 새 어휘 목록을 만들지 않는다.

| 기준 | 판정 |
|---|---|
| 0건 | 미달 |
| 질문의 고유 단서(영문 약어·고유명사·수치)가 근거에 하나도 없음 | 미달 |
| 질문이 "3건"이라 했는데 그보다 적게 모임 | 미달 |

`tools.question_clues()`가 단서를 뽑는다 — 영문 대문자 약어(VLGC), 한글 3자 이상 고유명사,
콤마 포함 숫자. 흔한 의문사·서술어(`얼마·무엇·어떻게·기준·관련`)는 뺀다.

처음엔 좁은 조건부터 다 풀었다: `date → month → topic 키워드 → year`.
그리고 "단서가 하나라도 늘면 진전으로 보고 교체"했다. **둘 다 틀렸다.**

| 깨진 것 | 원인 | 처방 |
|---|---|---|
| TR-ABS-001 (부재 함정) | "자기주식 취득" 0건 → **키워드를 풀어** 대량보유보고서를 끌어와 답을 지어냄 | 주제 키워드는 **절대 안 푼다**. 시간 조건만 푼다 |

> **완화는 질문 조건을 푸는 것이라 부재 함정과 정면충돌한다.**
> 없는 것은 없다고 답해야 하는데, 완화가 그걸 막으면 안 된다.

### 19-a. 정정본이 개수를 왜곡한다 (T4-O-017)

**증상.** "한미약품이 2023년에 투자판단 관련 주요경영사항으로 공시한 건은 총 몇 건인가"에

**원인.** 정정본 하나(2024-02-01)가 원공시 **3건**(2023-08-01)을 한꺼번에 정정했다.

**1차 수정 → 회귀.** 최신본이 같은 원공시가 둘 이상이면 원공시를 복원하게 했다.
해당 문항은 4/4로 고쳐졌는데 **T4-O-003이 깨졌다** — 복원된 원공시의 **폐기된 값**
(해지금액 정정 전 4,082,377,000,000)이 근거에 들어가 HCX가 그걸 집었다.

> **개수를 물으면 원공시 개수가 맞고, 값을 물으면 최신 정정본 값이 맞다.**
> 둘이 반대 방향이라 항상 복원하면 값 질문이 망가진다.

**2차 수정.** 질문이 개수를 묻는지로 가른다(`몇 건|총 N건|N건`). 둘 다 통과, 유형④ 18/18.

### 19-b. correction_map에 빠진 연결 484건 (TR-COR-003)

**증상.** 에코프로비엠 투자기간 종료일에 정정 전 값(2024-12-31)을 답했다. 정답은 2026-12-31.

**원인.** 원공시(2023-05-23)와 정정본(2024-10-22)이 `correction_map`에 **안 이어져 있다.**
`superseded_by[원공시] = None`. 그래서 연도 필터가 정정본을 잘라내고 `latest_version`이
따라갈 대상 자체가 없었다.

**조치 — 원본 데이터는 안 건드린다.** 명섭 형이 재임베딩 중이라 correction_map이 다시 만들어진다.
조회 시점에만 보완하고, 고쳐지면 이 코드는 그냥 안 걸리고 지나간다.

**조건을 좁게 잡은 이유.** "같은 기업 + 같은 제목"만으로는 안 된다 — 한 기업의
공급계약체결은 제목이 전부 같아서 **411건이 서로 엮인다.** 조건을 하나 더 붙였다.

> **정정본 본문에 원공시의 접수일이 적혀 있는가.**
> DART 정정공시는 본문에 원공시의 이사회결의일·계약일을 다시 적는다.
> 에코프로비엠 정정본에 `이사회결의일 2023-05-23`이 있고 원공시 접수일과 정확히 일치한다.

→ `collect`에 **`filer` 축**을 추가했다. 공백 표기 차이(`국민연금공단` vs `국민연금 공단`)까지

### 20-b. 중간 검산이 조사 때문에 무력화돼 있었다 ★

실험 18에서 넣은 단계 중간 검산이 **처음부터 헛돌고 있었다.**

질문에서 단서를 뽑아 근거에 있는지 확인하는데, 뽑은 단서가 원시 문자열이라
질문의 **"레인보우로보틱스에"**가 근거의 **"레인보우로보틱스"**와 안 맞았다.
한국어는 조사가 붙는다는 걸 놓쳤다.

**9개 단서 중 0개 매칭.** 그래서 매 질문마다 "단서를 하나도 못 찾음"으로 판정돼
**불필요한 완화가 항상 돌았다.** 검산이 품질을 지키는 게 아니라 매번 완화를 부르는
장치가 돼 있었던 것이다.

→ 조사를 떼는 `content_words`로 단서를 뽑게 고쳤다.

### 20-c. 프롬프트 한 줄이 57 → 55로 ★ 이번 실험의 핵심

`filer` 축을 플래너가 쓰게 하려면 프롬프트에 설명을 넣어야 한다. 한 줄 넣었다.
**무관한 두 문항이 깨졌다.**

| 문항 | 무슨 일이 났나 |
|---|---|
| T4-O-020 | 계획이 바뀌어 `validate`가 반려 → 폴백 경로로 감 |
| T6-O-005 | `yeartab`으로 가서 무관한 금액까지 합산 |

**먼저 비결정성부터 의심했다.** 같은 질문을 3회 돌려 계획 JSON을 비교했더니 **완전히 동일**했다.
플래너는 결정적이다. 그러면 원인은 하나다 — 내가 넣은 그 한 줄.

> **플래너 프롬프트는 전역 변수다.**
> 축 하나를 설명하려고 넣은 문장이 그 축과 아무 상관 없는 문항의 도구 선택을 바꾼다.
> 도구를 추가하는 비용은 "그 도구를 만드는 일"이 아니라 **"기존 계획 전체가 흔들리는 일"**이다.

이건 코드 수정과 성질이 다르다. 코드는 건드린 함수만 영향받지만
프롬프트는 어느 문항에 영향이 갈지 미리 알 수 없다. **전체 재측정 말고는 확인 방법이 없다.**

### 20-d. 되돌리지 않고 흡수한 방법

`filer` 축은 60선 대응에 필요하니 프롬프트를 되돌릴 수는 없었다. 대신 세 곳을 손봤다.

1. **반려 대신 강등** — `compare`인데 입력이 1개면 계획을 반려했다.
   반려는 폴백을 부르고 폴백은 더 비싸다. `mode`만 `list`로 낮추고 그대로 실행한다.
2. **자동 합산을 `collect` 결과에만** — `yeartab`/`find`가 가져온 문서에는 합계가 이미 적혀 있다.
   거기에 코드가 또 더하면 무관한 공급계약 금액까지 답에 섞인다.
3. **`yeartab` 범위 축소** — 연도별 표를 펼치는 도구인데 아무 대조 질문에나 붙었다.
   `매출구성|구성비|비중|품목별|제품별`이 있을 때만 쓰고, 아니면 `find`로 내린다.

### 20-e. 근거를 다 모으고도 순서 때문에 절반을 버렸다 (T6-O-002)

`근거recall 1.0`인데 오답이었다. 필요한 문서가 전부 근거에 들어갔다는 뜻이라 수집은 문제가 없었다.

두산퓨얼셀 **2025년 사업보고서 한 건에 필요한 값 4개가 전부** 들어있다.
정기보고서는 당기 옆에 전기·전전기를 같이 싣기 때문이다. 반대로 2023년 보고서에는
2025년 비중(78.94%)이 있을 수가 없다. **미래 값이다.**

그런데 근거가 계획 단계 순서대로 쌓여서 2023년 표가 앞에 왔고, HCX가 그것만 읽고 답을 끝냈다.

> 정보량이 다른 근거를 나란히 주면 앞엣것이 이긴다.
> **최신 정기보고서가 정보 우위**라는 건 코드가 아는 사실이니 순서는 코드가 정한다.

`yeartab`이 있던 자리 안에서만 최신 연도순으로 바꿨다. 다른 단계 순서는 건드리지 않는다.

### 20-f. 프롬프트로 세 번 실패한 것을 코드가 한 번에 끝냈다 ★

20-e 이후에도 T6-O-002는 4개 중 2개만 맞았다. 빠진 둘이 전부 표의 **합계(계)** 값이다.

확정치 블록에는 `계 = 260,886`이 적혀 있고 "합계(계) 금액도 함께 적어라"가
**블록 안에도, 합성 지시에도** 있었다. 그런데 HCX는 항목별 금액만 쓰고 합계 행을 버린다.

**여기서 5회 반복 측정을 시작했다.**

| T6-O-002 | 통과 |
|---|---|
| 프롬프트 강화 3회 | 5회 중 2회 (40%) |
| 코드가 합계 보강 | **5회 중 5회 (100%)** |

실험 19-c(범위 밖 안내)와 같은 결론이고 이번이 **세 번째**다.

> LLM에게 "빠뜨리지 마라"를 시키는 건 확률 게임이다. 코드가 확인해서 붙이면 100%다.
> 표의 당기 열에서 코드가 직접 읽은 값이면, 그건 코드가 말해야 한다.

### 20-g. 폴백 경로가 죽어 있었다 (NameError)

5회 반복 측정 중에 `slice6.py`에서 `NameError: used_annual is not defined`가 터졌다.
`gather_year`를 함수로 빼내는 리팩터링 때 변수 정의만 사라지고 사용부가 남았다.

플래너가 대부분을 처리해서 **정상 측정에서는 한 번도 안 드러났다.**
플래너가 실패해 폴백으로 넘어가는 순간에만 크래시한다.

**단일 측정으로는 절대 못 잡는 결함이다.** 실제 평가 중 플래너가 흔들리면 그 문항은 통째로 날아간다.

### 20-h. 채점셋이 같은 값의 두 표기를 따로 요구한다

T5-C-002는 `9,603,075,000,000`을 정확히 맞히고도 실패했다.
정답 패턴 2개 중 하나가 `9조 6,030억`이라 **같은 숫자를 한글로도** 써야 통과다(1/2 = 0.5 < 0.6).

평가셋에는 없는 유형이라 **진짜 일반화 시험**이다. 결과가 네 갈래로 갈렸다.

### 21-a. 진단이 두 번 빗나갔다 (OQ-59) ★

**첫 번째 가설 — 어휘 매칭 실패.** 구어 "연봉"이 공시 용어 "보수"와 안 맞는 줄 알았다.
검색을 직접 돌려 확인했다.

| topic | 근거 | '5억' 포함 |
|---|---|---|
| 연봉 / 보수 / 임원 보수 / 이사·감사 보수 | 각 5건 | 전부 True |

**틀렸다.** 어느 말로 찾아도 근거는 정확히 온다.

**두 번째 가설 — count 오해.** 계획을 보니 `"count": 1`이 있었다.
"제일 많이 받는"을 건수로 읽은 것이다. 후보 91건을 1건으로 뭉갰다.
질문에 건수가 없으면 count 를 무시하게 고쳤다. **여전히 거부했다.**

**진짜 원인 — 도구 선택.** 플래너가 `collect`(제목 검색)를 골랐다.
임원 보수는 사업보고서 「VIII. 임원 및 직원 등에 관한 사항」 **본문**에 있다.
공시 제목에는 존재하지 않는다.

> **제목에 없는 것을 제목으로 찾으면, 후보가 아무리 많아도 답은 0건이다.**

기존에 "제목 0건이면 본문 검색으로 승격"이 있었는데 **후보가 91건이라 발동하지 않았다.**
0건이 아니라 '엉뚱한 91건'이 문제였던 것이다.

두 가지를 고쳤다.
1. 승격 조건을 "0건" → "0건이거나 질문 단서를 하나도 안 담음"으로 확대
2. 보수·연봉·급여·직원·연구개발·생산능력·가동률·원재료·계열회사·종속회사·배당성향이
   topic 에 있으면 `collect` 를 `find` 로 돌린다

**목록에서 뺀 것.** "배당", "임원", "주주"는 공시 **제목**에도 쓰인다
(현금·현물배당 결정, 임원·주요주주특정증권등소유상황보고서, 최대주주 변경).
넣었으면 멀쩡히 돌던 제목 검색이 깨진다. 그래서 "배당성향"·"배당정책"으로만 좁혔다.

결과: `노태문 6,904백만원` + 근거 인용. **과잉 거부 없이 공시 범위 내 답변**이라
이 문항의 채점 포인트("무조건 거부는 감점")를 충족한다.
같은 수정으로 OQ-40(연구개발비)·OQ-33(가동률)·OQ-35(원재료)도 함께 풀렸다.

### 21-b. 구어는 뜻이 아니라 단어가 문제다 (OQ-58·60)

"엔씨 게임사업 쪼갠 거 뭐야?"가 사업보고서로 새서 답을 못 냈다.
그런데 **같은 사건을 문어체로 묻는 평가셋 TR-NAME-002는 통과한다.**
회사분할 공시는 멀쩡히 있고, "쪼갠"이라는 단어로 못 찾을 뿐이다.

구어를 공시 용어로 옮겨 topic 에 **덧붙인다**(덮어쓰지 않는다 — 원래 topic 이
맞았던 경우를 망치지 않기 위해서다). 쪼갠·분사→회사분할, 먹으려→대량보유 경영권,
인수한 거→최대주주 변경, 연봉→임원 보수, 빚→차입금.

그리고 일반인 말투로 물으면 답도 설명이어야 한다. 공시 서식 항목을 그대로 옮기지 말고
**질문의 전제가 공시 사실과 다르면 먼저 바로잡으라**는 지시를 조건부로 붙였다.

> **평가셋 58문 중 이 조건에 걸리는 문항은 0개다.**
> 실험 20-c에서 프롬프트 한 줄이 무관한 문항 2개를 깬 뒤로,
> 프롬프트를 건드릴 때는 걸리는 문항을 먼저 세어본다.

OQ-60 결과: "콜옵션 권리자인 삼성전자 / 최대주주는 아직 완전히 변경되지 않았습니다 /
8,550,439주(55.83%)" — **인수라는 잘못된 전제를 정확히 교정**했다.

### 21-c. 고치지 못한 것 — 표를 코드가 읽어야 한다 (OQ-51)

"삼성전자 CAPEX 추이와 매출 대비 비중"에 이런 답이 나왔다.

```plain text
CAPEX: 296,857,289백만원 (296조)
  유형자산 취득: 45,026,206백만원
  무형자산 취득:  4,104,861백만원
```

**합이 안 맞는다.** 매출(170조)보다 CAPEX가 크다는 자기모순도 그대로 낸다.
현금흐름표의 당기·전기·전전기 3열을 뒤섞어 숫자를 조합해 만들어낸 것이다.
`[귀속경고] 실존율 0.24` 가 이미 감지하고 있었지만 경고만 하고 답변은 나간다.

`compute` 에 나눗셈(`ratio`)이 없어서 HCX가 직접 나눈 것도 원인이라 op 를 추가했다.
**그것만으로는 안 고쳐진다.** 플래너가 `ratio` 를 고르지도 않았고,
애초에 표에서 CAPEX 값을 잘못 읽는 게 먼저다.

> **기권보다 나쁜 게 틀린 답을 확신 있게 내는 것이다.**
> 이 유형은 `gather_annual` 처럼 **코드가 표를 파싱해 확정치로 주입**해야 풀린다.
> 프롬프트로는 못 고친다 — 20-f에서 이미 확인했다.

남은 과제로 명시해 둔다. OQ-58(연도 없는 구어 + 별칭)과 OQ-57(연도 특정)도 미해결이다.

## 실험 22 — 60문 전수 대응: 평가셋이 못 잡던 버그가 나왔다

실험 21에서는 60선 중 앵커 미확인 문항만 골라 봤다. 이번엔 **60문 전부**를 돌렸다.
정답이 없는 목록이라 점수 대신 "부재 응답을 내는가"로 판정했다.

| | 결과 |
|---|---|
| 첫 전수 | 56/60 (실패 OQ-26·27·29·58) |
| 최종 | **59/60** |
| 평가셋 58문 | 56/58 유지 (회귀 없음) |

### 22-a. collect 가 별칭 기업에서 통째로 0건이었다 ★ 진짜 버그

```python
cands = [d for d in docs if d["corp_name"] == corp]   # 정확 일치만
```

코퍼스의 엔씨소프트 표기는 **"NC"**다. `norm_corp("엔씨소프트")` 는 "NC"를 제대로
돌려주는데 `collect` 가 그 함수를 안 쓰고 원문을 그대로 비교했다.

```plain text
collect("엔씨소프트")  ->  0건   (수정 전)
collect("엔씨소프트")  -> 12건   (수정 후)
```

**`find` 는 정규화를 거친다.** 그래서 같은 질문이 find 로 가면 통과했고,
평가셋의 TR-NAME-002(엔씨소프트 회사분할)는 계속 만점이었다.
경로가 갈리는 바람에 **한쪽이 통째로 죽어 있는데도 점수로는 안 드러난 것이다.**

정규화 이름으로 0건이면 원래 이름으로 되돌려 기존 동작을 보존한다.

> 평가셋 58문으로는 이 버그를 영원히 못 잡는다. 분포가 다른 질문을 돌려야 나온다.

### 22-b. 승격은 대체가 아니라 보강이어야 했다 ★ 이번 실험의 핵심

실험 21에서 OQ-59를 고치려고 "제목 검색 결과가 질문 단서를 못 담으면 본문 검색으로
**교체**"를 넣었다. 그게 OQ-58을 깨뜨렸다.

```plain text
키워드(분할) 4건 / 최신본 2건      <- 회사분할 공시를 정확히 찾음
-> 검산 미달(질문 단서 미포함)
-> 본문 검색 승격 / 검색 120건      <- 정답 2건 버리고 사업보고서를 끌어옴
```

질문 단서가 "쪼갠"·"게임사업" 같은 **구어**라 공시 본문에 있을 리가 없다.
멀쩡한 결과를 "단서 미포함"으로 판정하고 갈아엎었다.

**그래서 "제목 키워드가 실재하면 승격 금지"를 넣었더니 평가셋이 56 -> 55로 떨어졌다.**
T4-O-007(삼성SDI 확정발행가액 140,000)이 깨졌다. 그 값은 `collect` 가 담는
문서 앞부분 2,500자 **밖**에 있어서, 원래 승격된 find 가 주워오던 값이었다.

| | OQ-58 | T4-O-007 |
|---|---|---|
| 교체 (원래) | X 정답 버림 | O |
| 승격 금지 | O | X 확정가 누락 |
| **유지 + 보강** | **O** | **O** |

> **collect 와 find 는 대체재가 아니라 보완재다.**
> collect 는 문서 앞부분만 담고 find 는 뒤쪽을 채운다.
> 하나를 끄는 게 아니라 둘 다 쓰는 것이 답이었다.

제목 필터가 실제로 후보를 좁혔으면(trace 에 "키워드(...)"가 남으면) 그 결과를
버리지 않고 본문 근거를 **더한다**. 텍스트 앞 120자가 겹치는 것만 뺀다.

### 22-c. 구어는 도구마다 정반대로 다뤄야 한다

"엔씨 게임사업 쪼갠 거 뭐야?"에 구어 사전이 "회사분할"을 topic 에 **덧붙였더니**
`"게임사업 회사분할"` 이 되어 0건이 됐다. 제목 필터는 키워드를 **전부** 만족해야 남는다.

| 도구 | 처리 | 이유 |
|---|---|---|
| collect | 공시 용어로 **대체** | 제목 필터는 키워드를 다 만족해야 남는다 |
| find | 원래 topic 에 **덧붙임** | 벡터 검색은 문맥이 많을수록 정확하다 |

같은 정보를 도구에 따라 반대로 써야 했다.

### 22-d. 연도 환각과 건수 오해

```plain text
"삼성전자 요즘 뭐로 돈 벌어?"  ->  플래너가 year=2022 를 지어냄
                              ->  "코퍼스 범위 밖이라 확인할 수 없음"
```

프롬프트에 "질문에 연도가 없으면 year 는 null"이라고 **이미 적혀 있었다.** 안 지킨다.
질문에 연도가 하나도 없으면 코드가 뗀다. 건수(count)도 마찬가지로
질문에 "N건"이 적혀 있을 때만 인정한다("제일 많이 받는"을 1건으로 읽었다).

### 22-e. 고치지 않기로 한 것 — OQ-26

하이브 연구개발비 2023 vs 2025. 근거를 열어보니 이렇다.

```plain text
2023: "... 지급임차료 55,471 136,857 36,636 335,335
       경상연구개발비 51,473 144,898 381,626 798,286 ..."   <- 숫자 4개가 어느 기간인지 불명
```
