# 공시 Agent 완전 이해 가이드

우리가 만든 것 전부를 처음부터 끝까지 이해하기 위한 문서다.
코드 한 줄씩 읽는 대신 **흐름을 따라가며** 각 지점에서 무슨 일이 왜 일어나는지 본다.
읽고 나면 "여기를 이렇게 고치면 되겠다"가 나와야 한다.

---

# 0. 먼저 알아야 할 용어

이 문서 전체에서 반복해서 나온다. 여기서 한 번 정의하고 간다.

| 용어 | 뜻 |
|---|---|
| **DART** | 금융감독원 전자공시시스템. 상장사가 법에 따라 올리는 공시 문서가 모이는 곳 |
| **공시** | 회사가 투자자에게 알려야 하는 사실을 공개한 문서. 사업보고서·계약 체결·유상증자 등 |
| **정기공시** | 기간마다 반드시 내는 것. 사업보고서(1년)·반기보고서(6개월)·분기보고서(3개월) |
| **수시공시** | 사건이 생길 때마다 내는 것. 계약 체결·해지, 사채 발행, 신규 시설투자 등 |
| **정정공시** | 앞서 낸 공시의 내용을 고쳐 다시 내는 것. 제목에 `[기재정정]`이 붙는다 |
| **접수번호(rcept_no)** | 공시 하나에 붙는 고유 번호. 앞 8자리가 접수 날짜다 (예: `20250312000405` → 2025-03-12) |
| **청크(chunk)** | 문서를 검색에 쓰려고 잘라 놓은 조각. 우리 코퍼스는 257,186개 |
| **임베딩(embedding)** | 문장을 숫자 벡터로 바꾼 것. 뜻이 비슷하면 벡터도 가까워진다 |
| **벡터 검색** | 질문을 벡터로 바꿔서, 벡터가 가까운 청크를 찾아오는 방식 |
| **FAISS** | 벡터를 빠르게 검색하는 라이브러리 |
| **RAG** | Retrieval-Augmented Generation. 검색으로 근거를 찾아 LLM에게 주고 답을 쓰게 하는 방식 |
| **HCX (HyperCLOVA X)** | 네이버의 대규모 언어모델. 대회 규정상 우리가 쓸 수 있는 유일한 LLM |
| **슬롯(slot)** | 질문에서 뽑아낸 구조화된 정보. 기업명·연도·질의유형·찾는 항목 |
| **라우팅(routing)** | 질문을 어느 처리 경로로 보낼지 정하는 것 |
| **컨텍스트(context)** | LLM에게 함께 넣어주는 근거 자료 뭉치 |
| **환각(hallucination)** | 근거에 없는 내용을 LLM이 그럴듯하게 지어내는 것 |
| **기권(abstention)** | 모르는 것을 모른다고 답하는 것. 지어내는 것보다 낫다 |
| **근거recall** | 정답이 든 문서를 실제로 찾아왔는지의 비율. 채점 항목 |
| **정규식(regex)** | 글자 패턴을 기술하는 표기법. `\d{4}`는 숫자 4개를 뜻한다 |

# 1. 우리가 푸는 문제

대회는 **DART 공시 4,204건**을 주고, 그것으로 질문에 답하는 API 서버를 만들라고 한다.
주최측이 우리 서버에 질문을 HTTP로 보내면 우리는 이런 JSON을 돌려줘야 한다.

```json
{
  "question_id": "T1-C-001",
  "question": "삼성전자의 2025 사업연도 연결기준 매출액은?",
  "retrieved_context": "근거로 쓴 문서들 (접수번호 포함)",
  "think_trace": "어떻게 답에 도달했는지",
  "answer": "최종 답변"
}
```

**채점은 세 갈래**다.
1. **정답** — 답변에 정답 문자열이 들어 있는가 (`accept_patterns`)
2. **근거** — `retrieved_context`에 정답 문서의 접수번호가 있는가
3. **함정** — 답할 수 없는 질문에 제대로 거절하는가

질문은 여섯 가지 유형으로 나뉜다.

| 유형 | 이름 | 성격 | 예 |
|---|---|---|---|
| ① | 검색추출 Closed | 한 문서에서 값 하나 | "SK하이닉스 2024년 4월 시설투자 금액은?" |
| ② | 검색추출 Open | 한 문서에서 서술 | "청주 M15X 투자의 목적과 기간을 정리해줘" |
| ③ | 다중비교 Closed | 두 기업 비교 | "현대차와 기아의 2024년 영업이익 비교" |
| ④ | 다중수집 Open | 여러 건 모아 정리 | "신한지주 2024년 자금조달 내역" |
| ⑤ | 복합추론 Closed | 사건을 이어 추론 | "그 계약은 이후 해지됐나?" |
| ⑥ | 복합추론 Open | 두 시점 대조 서술 | "2023년과 2025년 매출 구성 변화" |

**Closed는 정답이 하나로 떨어지고, Open은 서술이 답이다.** 채점 방식이 다르다.
Closed는 정답 문자열 하나만 맞으면 되고, Open은 정답 패턴의 60% 이상을 담아야 한다.

# 2. 전체 흐름 — 질문 하나가 답이 되기까지

```
질문 문자열
    │
    ▼
┌─────────────────────────────────────────────────┐
│ ① extract.py — 질문을 슬롯으로 분해            │  HCX 1차 호출
│    "SK하이닉스 2024년 시설투자 금액"            │
│    → {corps:[SK하이닉스], year:2024,            │
│       qtype:1, item:"시설투자 금액"}            │
└─────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────┐
│ ② pipeline.normalize_slots — 타입 정리              │  LLM 안 씀
│    "4"→4, null→[], "2024년"→2024                │
└─────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────┐
│ ③ main 라우터 — 어느 slice로 보낼지 결정        │  LLM 안 씀
│    + 코드가 오분류를 되돌리는 보정 규칙 5종     │
└─────────────────────────────────────────────────┘
    │
    ├──▶ slice1  유형①②  벡터 검색
    ├──▶ slice3  유형③    기업별로 각각 검색
    ├──▶ slice4  유형④    검색 없이 목록 필터
    ├──▶ slice5  유형⑤    해지 공시를 기준점으로
    └──▶ slice6  유형⑥    연도별 수치 + 배경
    │
    ▼
┌─────────────────────────────────────────────────┐
│ ④ attribute.build_context — 근거 조립           │  LLM 안 씀
│    [근거 1/5] 사업보고서 (접수일 ...)           │
│    | 접수번호 ... | 기업명 | 섹션               │
└─────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────┐
│ ⑤ hcx.call_hcx — 답변 생성                      │  HCX 2차 호출
│    타임아웃·재시도·잘림 감지 포함               │
└─────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────┐
│ ⑥ pipeline.clean — 후처리와 검증                    │  LLM 안 씀
│    마크다운 제거 → 날짜 검증 → 귀속 검증        │
│    → 추측 어투 탐지                             │
└─────────────────────────────────────────────────┘
    │
    ▼
{answer, retrieved_context, think_trace}
```

**여기서 가장 중요한 설계 원칙이 보인다.**
HCX는 **두 번만** 등장한다 — ①질문 해석과 ⑤답변 생성.
찾기·고르기·검산·검증은 전부 파이썬 코드가 한다.

**왜 이렇게 했나.** LLM에게 "수천 건 중에서 알아서 찾아줘"를 시키면 흘리고 지어낸다.
우리가 실제로 겪은 실패다 — 근거 6건을 주고 정리하라 했더니 2건만 쓴 적이 있고,
"3건의 합계"를 물었는데 엉뚱한 3건을 골라 더한 적도 있다.
**코드는 세는 걸 절대 틀리지 않고, LLM은 문장을 잘 쓴다.** 각자 잘하는 것만 시킨다.

# 4. 각 단계 자세히

## 4-1. extract.py — 질문을 슬롯으로 분해

**하는 일.** 자연어 질문을 HCX에게 주고 JSON을 받는다.

```
"SK하이닉스가 2024년 4월에 공시한 신규 시설투자의 투자금액은?"
        ↓
{"corps": ["SK하이닉스"], "year": 2024, "qtype": 1, "item": "투자금액"}
```

**왜 필요한가.** 뒤의 모든 필터가 기업명·연도로 후보를 좁힌다.
그러려면 질문에서 그 값을 먼저 뽑아내야 한다.

### 여기서 겪은 문제와 처방

**문제 1 — HCX가 JSON을 흘린다.**
`temperature=0`(무작위성 0)인데도 같은 질문에 마지막 `}`가 빠진 응답이 왔다.
2회 중 1회 재현. 우리가 못 고치는 HCX 쪽 문제다.

→ **처방: 꼬리 복구 + 재시도.** `parse_json()`이 닫는 괄호 후보(`}`, `"}`, `"]}`)를
하나씩 붙여보며 파싱을 시도한다. 그래도 안 되면 한 번 더 호출한다.

**여기에 함정이 있었다.** 처음엔 파싱이 성공하면 바로 통과시켰는데,
`{"corps": ["LG", "yea` 처럼 **키 이름을 쓰다 잘린** 조각에 `"]}`를 붙이면
`{'corps': ['LG', 'yea']}`가 되어 **없는 기업 'yea'가 생긴다.**
문법은 맞는데 뜻이 틀린 것이다.

→ **교정: 내용까지 검문한다.** 파싱 결과에 `qtype`이 있어야만 통과시킨다.
정상 응답에는 항상 있고, 중간에 잘린 조각에는 없다.

> **배울 점**: "검증되는 복구"의 검증은 문법이 아니라 **내용**이어야 한다.

**문제 2 — 같은 질문에 슬롯이 매번 달라진다.**
이게 더 심각했다. 같은 문항을 3번 돌렸더니 **실패·실패·성공**이 나왔다.
슬롯이 흔들리면 라우팅과 필터가 통째로 달라진다.
**측정이 흔들리면 개선인지 운인지 구분할 수 없다.**

→ **처방: 슬롯 캐시.** 질문 문자열을 키로 결과를 파일에 저장한다(`slot_cache.json`).
같은 질문은 같은 슬롯을 쓴다.

**문제 3 — 코드펜스가 한 줄로 온다.**
HCX가 ```` ```json {...} ```` 를 개행 없이 한 줄로 보내면
`split("\n")[1]`이 `IndexError`로 죽었다. 그 예외는 복구 로직 **앞에서** 터져
재시도조차 못 했다.

→ **처방: `strip_fence()`가 줄이 하나뿐인 경우를 따로 처리한다.**

## 4-2. pipeline.normalize_slots — 타입 정리

**하는 일.** HCX가 준 슬롯의 타입을 한 곳에서 정리한다.

```
{"corps": null, "year": "2024년", "qtype": "4", "item": null}
        ↓
(4, [], [2024], "")
```

**왜 한 곳에 모았나.** 예전에는 slice마다 방어를 따로 했는데,
slice6만 `item=None`에 무방비여서 크래시가 났다.
**입구에서 한 번 정리하면 그런 편차가 사라진다.**

정리하는 것 넷:
- `qtype` — 문자열 `"4"`가 오면 `4 == "4"`가 False라 모든 라우트를 미끄러진다
- `corps` — `null`이면 TypeError, 문자열이면 `['삼','성','전','자']`로 쪼개진다
- `year` — 문자열·리스트·정수가 다 온다. 정수 리스트로 통일
- `item` — 리스트로 올 때가 있다. `str()`로 감싸면 `"['매출액', ...]"`가 되어 검색어가 망가진다

## 4-3. main 라우터 — 어디로 보낼지 정한다

HCX가 정한 `qtype`을 그대로 믿지 않고 **코드가 검산한다.**

| 보정 규칙 | 조건 | 이유 |
|---|---|---|
| ③ → ⑥ | 기업 1곳 + 연도 2개 | 기업 비교일 수가 없다 |
| ③ → ① | 기업 1곳 | slice3은 기업 2곳이 없으면 근거 없이 끝나 정답이 불가능 |
| ⑥ → ③ | 기업 2곳 | 한 기업이 조용히 사라진다 |
| ⑥ → ④ | 기업 1곳 + 사건 어휘(발행·증자·사채·계약·투자) | 벡터 검색이 정기보고서 수천 청크에 묻힌다 |
| ①② → ④ | "N건", "여러 건" | 단일 검색으로 못 푼다 |
| ①②④ → ⑤ | "이후 어떻게" + 날짜 | 원공시만 찾고 후속을 못 본다 |

**이 보정이 왜 중요한가.** 실측으로 확인한 것 — 슬롯 캐시를 열어보니
"3건의 합계"를 묻는 질문이 `qtype: 1`로 분류돼 있었다.
**유형④ 개선을 아무리 해도 그 문항에 닿지 않고 있었다.**

> **원칙**: LLM이 분류하고, 코드가 검산한다.
> 프롬프트는 확률적으로 틀리지만 코드 검사는 항상 같은 답을 낸다.

## 4-4. slice1 — 유형①② (한 문서에서 찾기)

가장 기본이 되는 경로이자, **공통 부품이 모여 있는 파일**이다.

### 흐름

```
질문 → 벡터 검색 120건
     → 기업 필터
     → 연도 필터 (정정 체인 포함)
     → 폐기 원공시를 최신 정정본으로 교체
     → 별도/연결 근거 직행 보강
     → 별도/연결 재정렬
     → 상위 5건
     → 근거 조립 → HCX
```

### 핵심 부품들

**`year_of(h)` — 연도 판정**

청크에는 `base_year`(기준연도)가 있는데 **정기보고서에만 채워져 있다.**
수시공시는 전부 `None`이다. `None == 2024`는 항상 거짓이라,
연도를 지정한 질문에서 주요사항보고서·거래소공시가 **카테고리째 탈락**한다.

→ `base_year`가 없으면 접수일 연도로 대신한다.

**`chain_years(h)` — 정정 체인을 거슬러 올라간 사건 연도**

이게 사명변경 문항을 푼 열쇠다.

문제: LIG 인도네시아 경찰 계약은 2023-04-14에 체결됐는데,
**정답 금액이 든 청크 7개가 전부 2024~2026년 접수**였다.
정정본만 검색에 잡히기 때문이다. `year=2023` 필터에서 전멸했다.

→ 연도 판정을 "자기 접수연도"가 아니라 **"정정 체인을 거슬러 올라간 사건 연도 집합"**으로 바꿨다.
`base_year`가 있는 정기보고서는 손대지 않아 재무 문항 경로는 그대로다.

```
정정본 20250711 → (거슬러) 원공시 20230414
   → 연도 집합 {2025, 2023} → year=2023 통과 ✓
```

**`swap_superseded(hits)` — 폐기된 원공시 교체**

문제: 레인보우로보틱스 콜옵션 질의에서 **폐기된 원공시만 근거로 들어오고
정정본은 검색 결과에 아예 없었다.** 원공시에는 정정 전 문구
"행사 당시 시가 및 경영권 프리미엄"이 있는데, 그게 채점의 **금지 패턴**이었다.

→ 검색 결과에 폐기 문서가 있으면 코드가 그 자리를 최신 정정본 청크로 바꾼다.

> 프롬프트로 "정정 후 값만 써라"라고 해봐야 **정정 후 값이 컨텍스트에 없으면** 소용없다.
> 이게 프롬프트와 코드의 역할 경계를 보여주는 사례다.

**`scope_rerank` / `scope_backfill` — 별도/연결 구분**

질문이 "별도재무제표"를 지정했는데 우리가 해외 종속법인 표를 집는 일이 있었다.

**낱말로는 못 고른다는 게 데이터로 확인됐다.**
정답이 든 요약별도재무정보 청크에는 '별도'가 **0회**이고,
오답을 만든 싱가포르 법인 표에는 '별도재무제표 기준으로 작성'이 **2회** 박혀 있다.
표 제목이 청킹 경계에서 앞 청크로 잘려나간 탓이다.

→ 낱말 대신 세 가지로 층을 나눈다:
① 단위 선언이 외화뿐인가(해외 법인 표) ② '연결' 밀도 ③ 섹션 경로

그리고 **재정렬만으로는 부족하다.** 재정렬은 검색이 물어온 것 안에서만 순서를 바꾸는데,
삼성화재 2024년 청크가 2,495건이라 정답이 검색 상위에 못 들어오면 소용이 없다.
그래서 `scope_backfill`이 색인에서 직접 끌어와 앞에 끼운다.

**`SLIM` — 경량 색인 (배포를 살린 부품)**

여러 함수가 "이 기업, 이 연도, 이 섹션"으로 **전수 스캔**을 해야 한다.
그러려면 257,186건이 메모리에 있어야 하는데, 본문까지 들고 있으면 **11.3GB**가 된다.
배포 목표는 4GB다.

→ **본문을 뺀 메타데이터만** 담은 색인을 따로 만든다.
전수 스캔은 여기서 하고, 후보가 좁혀진 뒤 필요한 본문만 꺼낸다.

부수 효과가 하나 더 있다. 서버의 메모리 다이어트가 켜지면 `s.meta`는
**위치 접근만 지원하는 SQLite 지연조회 객체**로 바뀌는데,
경량 색인을 쓰면 순회를 안 하므로 그 상태에서도 돈다.

> **다이어트가 꺼지면 OOM, 켜지면 크래시**였던 상태를 한 번에 풀었다.

## 4-5. slice3 — 유형③ (두 기업 비교)

가장 단순하다. **기업마다 따로 검색한다.**

```python
hits_a = gather(기업A, 연도, 항목)
hits_b = gather(기업B, 연도, 항목)
context = [기업A 근거] + [기업B 근거]
```

**왜 따로 검색하나.** 명섭 형 가이드에 적힌 알려진 한계다 —
"다중 기업 비교 질의는 검색이 한쪽으로 쏠린다."
한 번에 검색하면 한 기업 문서가 상위를 다 먹는다.

## 4-6. slice4 — 유형④ (여러 건 수집)

**벡터 검색을 아예 안 쓴다.** 문서 목록(manifest)을 직접 거른다.

```
기업 필터 → 연도 필터 → 제목 키워드 필터
    → 정정 체인 그룹핑 → 최신본 교체
    → 질문에 적힌 월로 좁히기 → 질문 용어로 좁히기
    → 근거 조립
```

**왜 검색을 안 쓰나.** 유형④는 "전부" 유형이다.
"자금조달 내역을 정리해줘"는 6건이면 6건을 다 가져와야 한다.
벡터 검색은 본질적으로 "가장 비슷한 k개"를 주므로 조용히 누락된다.
**필터는 조건에 맞는 전부를 주니 재현율 100%가 구조적으로 보장된다.**

### 정정 처리 두 겹

**`group_chains`** — 같은 사건의 원본과 `[기재정정]`본을 묶어 최신 1건만 남긴다.

**`latest_version`** — 그것만으로는 부족했다.
연도 필터가 먼저 돌기 때문에 **이듬해 접수된 정정본은 이미 잘려나가 있고**,
그러면 `group_chains`는 폐기된 원본을 "정정 없는 단독 체인"으로 통과시킨다.

실측: (기업, 연도) 46개 조합 중 **10개에서 폐기본이 반환**됐다.
신한지주 12/5 건은 2025년 2월 정정으로 채무상환자금이 **2,200억 → 3,500억**으로 바뀌었는데
우리는 폐기값을 답하고 있었다.

→ `correction_map`을 **연도와 무관하게** 따라가 최신본을 찾는다.

**사이클 가드가 필수다.** correction_map에 상호 참조가 7건 실재한다
(A가 B를 대체하고 B가 A를 대체한다고 등록). 가드 없이 따라가면 무한루프로 프로세스가 멈춘다.

### 후보 좁히기

**`asked_months`** — 질문에 "2024년 1월"이 적혀 있으면 그 달로 좁힌다.
연도로만 거르면 17건이 되는데, 그중 어느 것이 질문 대상인지 고르는 일이 LLM에 넘어간다.

**주의점이 하나 있다.** 월이 명시된 연도만 좁혀야 한다.
"2023년 초 유상증자와 2024년 10월 전환사채"에서 `2024년 10월`만 보고 좁히면
**2023년 유상증자가 통째로 사라진다.**

**`question_terms`** — 질문의 영문 대문자 약어(VLGC·VLAC)로 본문을 거른다.

**`pick_keywords`** — item을 통째로 쓰면 안 된다.
HCX는 `"신규시설투자 금액"`이라 주는데 실제 보고서명은 `"신규시설투자등"`이라
부분일치가 실패해 0건이 된다.
→ 별칭 사전 → 없으면 **후보 제목에 실제로 등장하는 토막만** 남긴다
→ 하나도 없으면 키워드 필터를 아예 안 건다(거짓 부재를 만드는 것보다 낫다).

### 컨텍스트 예산제

공시 1건당 첫 청크 800자만 넣으면 자금조달 목적 내역·이자율처럼 표 뒤쪽 수치가 잘린다.
→ `budget = 14000 // 건수`. 건수가 적으면 넉넉히, 많으면 짧게. 총량을 일정하게 유지한다.

## 4-7. slice5 — 유형⑤ (체결 ↔ 해지 연결)

**해지 공시를 기준점(앵커)으로 잡는다.**

**왜 해지에서 출발하나.** 양쪽을 이어야 할 때는 세 가지를 만족하는 쪽에서 시작한다.
① 더 희소하고 ② 전원이 정답에 포함되고 ③ 단서를 쥐고 있는 쪽.

- 체결 공시는 1,100건이 넘는다. 해지는 기업당 0~9건.
- 해지 공시는 전원이 답의 일부다(해지가 있었다는 증거 그 자체).
- 해지 공시 본문에 **원 계약의 상대방·계약일**이 적혀 있다. 체결 공시에는 미래 정보가 없다.

### 겪은 문제들

**연도 필터가 해지를 죽였다.** "2024년 10월 체결한 계약 중 해지된 것"에서
`year=2024`가 해지 앵커에도 걸려, **2025년에 난 해지가 전멸**했다.
→ 해지 앵커에는 연도 필터를 걸지 않는다.

**짝짓기가 11전 11패였다.** 원래는 "해지일 이전 최신 2건"을 접수일 순으로 골랐는데,
공급계약이 수십 건 동시 진행되는 건설사에서는 최신 2건이 진짜 짝일 이유가 없다
(현대건설은 후보가 89건). 독립 측정에서 공급계약 recall@2가 **0/11**이었다.
→ `pick_starts`가 **해지 공시 본문과 단어가 겹치는** 체결 공시를 고른다.

**정정본이 해지를 두 번 세게 만들었다.** 원본과 `[기재정정]`본이 둘 다 '해지'를 포함해
개수 계약("총 N건")의 N이 부풀려졌다.
→ `group_chains` + `resolve_latest`를 해지 앵커에도 적용한다.

## 4-8. slice6 — 유형⑥ (두 연도 대조)

**근거를 두 갈래로 모은다.**

```
수치 근거 — 벡터 검색 (얼마인가)
배경 근거 — 섹션 필터 직행 (왜 그런가)
```

**왜 두 갈래인가.** 실측으로 배운 것이다.
"매출을 비교하고 배경을 설명해줘"에 검색어를 `"기업 연도 매출액"`으로 하면
재무제표 숫자 청크만 온다. **배경은 다른 섹션(경영진단·사업의 개요)에 있다.**
값이 있는 곳과 이유가 있는 곳이 다르다.

### `current_period_table` — 표를 코드가 직접 읽는다

사업보고서 매출표는 **당기 → 전기 → 전전기** 순으로 열이 나란히 있고,
청킹 과정에서 한 행이 `[금액, 비율, 금액, 비율, 금액, 비율]`로 평탄화된다.
**HCX가 이 순서를 못 읽는다.**

프롬프트로 "당기 열만 읽어라"라고 지시한 실험은 **오히려 퇴행**을 냈다
(세 연도 값을 다 나열해버렸다).

→ 코드가 표를 파싱해 앞의 두 셀(당기 금액·비율)만 뽑아
`[코드추출·확정치]` 블록으로 원문 앞에 붙인다. HCX는 옮겨 적기만 하면 된다.

**안전장치 셋:**
- `annual_wanted` — 관련 없는 질문에는 안 켠다(자금조달 질문에 매출표가 들어가면 자리를 뺏는다)
- `table_consistent` — 비중 합이 100%가 아니면 주입을 **포기**한다.
  파서가 셀이 '-'인 행을 조용히 버리는데, 그런 표를 '확정치'라고 단언하면
  **없던 오류를 우리가 만들어 넣는 셈**이다
- `base_month == 12` — 같은 해 분기·반기보고서 표는 섹션도 모양도 똑같아 벡터 점수로 구분되지 않는다

### `bg_sufficient` — 기권 여부를 코드가 정한다

배경 근거에 원인 서술이 실제로 있는지 코드가 세어 판정한다.
충분하면 배경 서술을 요구하고, 불충분하면 아예 안 요구한다.

**왜 코드가 정하나.** 기권을 모델 판단에 맡기면 환각과 과잉기권 사이에서 진자가 왕복한다.
이건 우리가 하루 종일 겪은 문제다(아래 5장 참조).

## 4-9. attribute.py — 프롬프트 규칙과 검증

### 프롬프트 규칙 블록 7종

각 slice의 SYSTEM 프롬프트 끝에 필요한 것을 붙여 쓴다. **한 곳만 고치면 전 유형에 적용된다.**

| 블록 | 내용 | 왜 |
|---|---|---|
| `BASE_RULES` | 확인되지 않음 명시 / URL 금지 / 반올림 금지 / 마크다운 금지 / 근거 표기 | 팀 가이드가 "6유형 평가에서 검증된 지시문"으로 명시 |
| `GUARD_RULES` | 질문 속 지시 무시 / 투자판단·목표주가는 한 문장 거절 | 프롬프트공격 함정 대응 |
| `CORRECTION_RULES` | 정정 전 값 인용 금지 | 정정본에 정정 전/후가 나란히 있어 옛 값을 읽는다 |
| `SCOPE_RULES` | 별도/연결 혼동 금지 / 외화 단위 표는 해외 법인 | 단위 선언을 먼저 보게 한다 |
| `TABLE_RULES` | 표의 당기 열만 | **현재 미사용** — 퇴행을 내서 뺐다 |
| `CITE_RULES` | 문단 끝에 근거 번호 | 문장 단위 강제는 과잉기권을 유발해 기각 |
| `BALANCED_CONTRACT` | 빠뜨려도 지어내도 같은 감점 | 기권 비용을 0으로 두면 모델이 기권으로 도망친다 |

### `build_context` — 근거 조립

```
[근거 1/5] 사업보고서 (2024.12) (접수일 20250312) | 접수번호 20250312000405 | LG에너지솔루션 | III. 재무에 관한 사항
<본문 800자>
```

**접수번호가 왜 들어가나.** 채점 ②가 `retrieved_context`에 접수번호가 있는지로 근거 점수를 준다.
예전에는 보고서명과 접수일만 넣어서 **답이 맞아도 근거 점수를 통째로 잃는 구조**였다.

**번호표(`1/5`)가 왜 있나.** 이게 곧 **개수 계약**이다.
코드가 `len()`으로 정확히 아는 개수를 프롬프트에 박아
"총 N건, 하나도 빠뜨리지 마라"고 계약을 건다.
실측으로 누락이 해결됐다(신한지주 2/6 → 3/3, 두산퓨얼셀 3/4 → 4/4).

### `check_grounding` — 답변이 근거에 있는 말로 쓰였는지 검사

답변을 문장으로 쪼개고, 각 문장의 **서술 내용어**가 근거에 실존하는지 비율을 잰다.
임계(0.5) 미만이면 무근거로 보고한다.

**설계에서 실측으로 정한 것 셋:**

1. **수치는 검사 대상에서 뺐다.** 답변은 "25조 6,196억원", 원문은 "25,619,585 백만원".
   단위 변환과 반올림 때문에 문자열 대조로는 **멀쩡한 수치를 오탐한다**(실제 발생).
2. **3자 이상 한글은 2자 어간까지 인정한다.** '매출액'과 원문 '매출' 같은 파생 차이.
   이 완화로 오탐이 1건 → 0건이 됐다.
3. **정당한 기권 문장은 면제한다.** "확인되지 않습니다"는 원래 근거에 없는 말이다.
   이걸 환각으로 잡으면 모델에게 "기권도 감점"이라는 잘못된 신호를 준다.

### `redact` — 삭제 상한

무근거 문장을 지우되, **잘라낼 문장이 전체의 40%를 넘으면 아예 안 자른다.**
검증기의 오탐이 곧 과잉기권의 코드판이라, 이 상한이 없으면 방어선이 흉기가 된다.

**현재는 `warn` 모드다.** 경고만 찍고 답변은 안 건드린다.
평가셋으로 오탐률을 재기 전에 자르면 위험하다.

## 4-10. hcx.py — 호출 계층

`requests.post`가 6곳에 흩어져 있었고 **여섯 곳 모두 타임아웃이 없었다.**
requests의 기본 타임아웃은 **무한대**다. HCX가 응답을 안 주면 그 요청이 영원히 멈춘다.
API 서버에서 이건 크래시보다 나쁘다 — 로그도 없이 무응답이 된다.

→ 호출을 한 함수로 모으고 그 안에서만 관리한다:
타임아웃(연결 5초·응답 60초) / 429·5xx 재시도 2회 / 200 아니면 예외 대신 `(None, 사유)` /
`stopReason`이 `length`면 잘림 경고.

**예외를 절대 밖으로 던지지 않는다.** 호출한 쪽은 `text is None`인지만 보면 된다.

# 4-11. 플래너 — 유형 하나 고르기에서 단계 조합으로 (2026-08-20 신설)

여기까지 읽은 구조에는 천장이 하나 있었다. **질문 하나 = 유형 하나 = slice 하나**다.

## 무엇이 문제였나

"카카오 사채 전부와 삼성전자 사채 전부를 연도별로 비교해라"는 세 가지가 필요하다.
카카오 수집, 삼성전자 수집, 그리고 비교. 그런데 라우터는 유형 번호 **하나**만 고르므로
셋 중 하나만 하고 나머지는 버린다. 버린 자리를 LLM이 지어내면서 환각이 난다.

명섭 형이 이걸 정확히 짚었다 — "qtype 발상은 좋은데 하나로만 처리하면 복합 질의에 바로 환각."

경욱 형이 평가셋을 30문에서 38문으로 늘리면서 신규 8문 중 4문이 정확히 이 유형이었다.

| 문항 | 필요한 단계 |
|---|---|
| T4-O-007 | 유증 **원본** 조회 + **최종본** 조회 + 비교 |
| T5-C-004 | 10/30 원공시 찾기 + 정정 계보 추적 |
| TR-MIX-001 | 2022년 조회 + 2023년 조회 (2022는 코퍼스 범위 밖) |
| T1-C-006 | "가장 최근" 판정 |

**각각에 if문을 박으면 그 4문만 통과하는 코드**가 된다. 그건 평가셋 암기지 일반화가 아니다.

## 바꾼 구조

```plain text
(이전)
질문 → HCX "유형 몇 번?" → 유형④ → slice4 → HCX 답변

(현재)
질문 → HCX "단계 목록 짜라" → 코드 검증·보정 → 도구 여러 개 실행 → HCX 합성
```

**HCX 호출 횟수는 2번으로 똑같다.** 첫 호출의 출력이 '숫자 하나'에서 '단계 목록'으로 바뀐 것뿐이다.

예를 들어 "삼성SDI 유증의 예정가와 확정가는?"이면 이런 계획이 나온다.

```json
{"steps":[
   {"id":"s1","tool":"collect","corp":"삼성SDI","year":2025,"topic":"유상증자","version":"original"},
   {"id":"s2","tool":"collect","corp":"삼성SDI","year":2025,"topic":"유상증자","version":"latest"}],
 "answer":{"mode":"compare","inputs":["s1","s2"]}}
```

단순 질문이면 단계가 1개라 기존과 똑같이 돈다.

## 도구 — 기존 slice를 버리지 않는다

각 slice가 하던 일은 둘로 나뉜다. **찾기**와 **HCX 불러서 답변 만들기**.
플래너 구조에서는 앞쪽만 떼어내 '도구'로 쓰고, 답변 만들기는 마지막에 한 번만 한다.

<table>
<tr><td>도구</td><td>어느 slice에서 왔나</td><td>무엇을 하나</td></tr>
<tr><td>`collect`</td><td>slice4 필터 체인</td><td>공시 **제목**으로 거른다. 기업·연도·키워드 → 정정 그룹핑 → 최신본</td></tr>
<tr><td>`find`</td><td>slice1 `retrieve()`</td><td>공시 **본문** 벡터검색 + 정정교체 + 별도/연결 보강·재정렬 **전부**</td></tr>
<tr><td>`trace`</td><td>slice5 + 신규</td><td>해지 공시 앵커 **+ 원공시의 정정 계보** (철회는 정정본으로 나온다)</td></tr>
<tr><td>`yeartab`</td><td>slice6 `gather_year()`</td><td>연도별 당기 표 코드파싱 + 배경 근거</td></tr>
<tr><td>`compute`</td><td>신규</td><td>합·차·증감률을 **파이썬이** 계산</td></tr>
</table>

`collect`에 축 세 개가 새로 생겼다. 이게 신규 문항들을 푼 열쇠다.

- **`version`** — `original`(정정 전 원본) / `latest`(최신 정정본, 기본) / `all`(체인 전체)
- **`recency=latest`** — rcept_dt 내림차순 1건. "가장 최근"을 코드가 정한다
- **`date`** — 특정 접수일

## 코드가 LLM을 되돌리는 자리 6곳 ★

여기가 이 구조의 핵심이다. 플래너가 계획을 잘못 짜는 경우가 실측으로 6가지 나왔고,
**전부 코드가 되돌린다.** 프롬프트로 고치려 한 것은 두 번 다 실패했다.

<table>
<tr><td>#</td><td>플래너가 낸 실수</td><td>코드가 하는 일</td></tr>
<tr><td>1</td><td>기업명에 `005930`(종목코드), `한화 에어로스페이스`(띄어쓰기), `LIG넥스원`(옛 사명)</td><td>`norm_corp` — ALIAS + 종목코드/통용명 표 + 공백 제거로 manifest 정식명에 맞춘다</td></tr>
<tr><td>2 ★</td><td>**날짜를 지어낸다.** "2023년 4월"에 `date:"20230401"`(4월 1일)</td><td>질문 원문에서 연·월·일 패턴을 정규식으로 뽑아, 계획의 date가 그 집합에 없으면 **떼고 month로 낮춘다**</td></tr>
<tr><td>3</td><td>제목에 없는 내용(최종 상호·콜옵션 조건)을 collect로 찾음</td><td>collect가 0건이면 **find로 승격**</td></tr>
<tr><td>4</td><td>단일 연도 재무수치를 yeartab으로 보냄</td><td>yeartab이 계획에 하나뿐이면 = 단일 연도 질문 → **find로 강등**. slice6 경로엔 별도/연결 보강이 없다</td></tr>
<tr><td>5</td><td>"3건의 합계"인데 후보 7건 중 아무거나 3건</td><td>질문의 영문 약어(VLGC·VLAC) 빈도로 **코드가 상위 N건 선별**</td></tr>
<tr><td>6</td><td>"이후 **해지된**"인데 trace를 안 씀</td><td>후속 추적 어휘가 있는데 trace 단계가 없으면 **하나 더한다**(빼지 않고 보탠다)</td></tr>
</table>

**2번이 가장 값진 발견이다.** date는 접수일 정확 일치 필터라 하루만 틀려도 0건이 되고,
문항이 통째로 날아간다. 그런데 에러가 안 나서 "공시가 없다"는 그럴듯한 오답이 나온다.

**6번의 판정 어휘는 기존 라우터의 유형5 승격 규칙을 그대로 가져왔다.**
`이후 어떻게|후속|결국|해지된|해지됐|취소된` — 새 어휘 목록을 만들지 않았다.

## 여기서 배운 것 ★

플래너 1차 측정이 **23/38로 폭락**했다. 34/38이던 게 11문이 깨졌다.

원인의 절반은 **도구가 기존 slice의 보정을 안 물려받은 것**이었다.
`find`를 만들 때 맨 벡터검색만 감쌌더니 정정본 교체·별도/연결 보강·사명변경이 한꺼번에 사라졌다.

> 명섭 형 진단 중 "라우터 보정은 한정된 질문용 if문이라 사실상 쓸모없다"는 **절반만 맞았다.**
> 그 보정들을 빼자 11문이 깨졌다. 보정은 버릴 게 아니라 **계획 검증기로 옮기는 것**이 맞았다.
> 23 → 38로 되돌린 작업이 정확히 그것이다.

# 4-12. HCX가 4시간 동안 응답을 안 준 사건 (실험 17)

결과 파일의 지연 상위를 훑다가 한 문항이 **16,236초(4시간 30분)**로 찍힌 걸 봤다.
같은 문항이 다른 회차에서는 7초였다.

**원인.** `requests`의 `timeout=(5, 60)`은 **(연결 5초, 바이트와 바이트 사이 간격 60초)**다.
**전체 시간 상한이 아니다.** 우리 엔드포인트는 `clovastudio.stream.ntruss.com` — 스트리밍이라
서버가 60초 안에 조금씩만 흘려보내면 read timeout이 매번 초기화된다.

**왜 치명적인가.** 주최측은 질의를 **순차로** 보낸다. 한 건이 4시간 물고 있으면 그 문항만
무응답이 아니라 **뒤의 모든 문항이 멈춘다.** 우리 코드는 예외를 안 던지므로 크래시도 로그도 없다.

**조치.** `hcx.py`에 벽시계 상한을 따로 걸었다. requests 자체로는 못 끊으므로
**데몬 스레드**에 요청을 넣고 `join(wall)`로 끊는다.

```plain text
계획 호출  wall=20초
합성 호출  wall=45초   (HCX_WALL_LIMIT 환경변수로 조정)
```

끊긴 스레드는 남지만 `daemon=True`라 프로세스 종료를 막지 않는다.
재시도도 남은 예산 안에서만 하고, 실패 시 반환은 기존과 같은 `(None, 사유)`라
호출부 폴백이 그대로 작동한다.

**용어.** 벽시계 시간(wall clock)은 실제로 흐른 시간이다. CPU가 일한 시간이나
"마지막 바이트 이후 경과"와 구분해서 쓴다.

# 5. 가장 중요한 교훈 — 환각과 과잉기권

이 시스템에서 제일 오래 싸운 문제다. 개선 방향을 잡으려면 이걸 알아야 한다.

## 무슨 일이 있었나

**(A) 환각.** 유형⑥ 질문에 수치는 완벽했는데 배경 서술이 이랬다.

> "전기차 수요 둔화 우려와 메탈 가격 하락 등이 영향을 미쳤을 가능성이 있습니다.
> 고금리·고물가로 소비자들의 구매 심리가 위축되면서…"

투입한 근거와 대조하니 **'메탈 가격'과 '북미'만 실존**했다.
나머지는 전부 모델이 학습한 세계 지식이다.
근거에서 진짜 하나를 집고 나머지를 그럴듯하게 엮은 것이다.

**(B) 과잉기권.** 이를 막으려고 프롬프트에 금지 항목을 명시하고
추측 어투를 금지했더니 **배경 전체가 "공시에서 확인되지 않습니다"로 사라졌다.**
근거에 '메탈 가격 하락'과 '북미 수요'가 멀쩡히 있는데도.

## 왜 그렇게 됐나 — 논문이 설명한다

Why Language Models Hallucinate(2025)의 Observation 1:
**이진 채점에서 기권은 엄격히 열등한 전략**이며,
모델이 기권을 택하려면 오답 감점이 `t/(1-t)` 이상이어야 한다.

우리는 정반대를 했다. **근거를 인용해 서술하는 비용**(정확한 인용·출처 표기·금지어 회피)만 올리고
**기권의 비용은 0으로 뒀다.** 모델은 합리적으로 싼 길을 택했다.

LongCite(2024)는 두 방식을 직접 비교했다.
생성과 인용을 **동시에** 시키면 인용 F1은 얻어도 정확성이 5% 떨어지고,
답변을 먼저 만들고 **인용을 나중에 붙이면** 정확성이 그대로였다.

## 그래서 어떻게 했나

**원칙: 생성은 자유롭게, 검열은 코드가.**

1. 프롬프트에서 금지 나열을 **뺐다**
2. `BALANCED_CONTRACT`로 **기권에도 비용을 부과**했다
3. 문장 단위 인용 강제는 **채택하지 않고** 문단 단위만 요구했다
4. 진짜 판정은 `check_grounding`이 **모델 표기와 무관하게** 독립 재계산한다
5. 기권 여부는 `bg_sufficient`가 **코드로** 정한다

> **한 줄 요약**: 환각과 과잉기권은 같은 손잡이의 양끝이다.
> 프롬프트로 어느 쪽을 밀어도 반대쪽이 튄다.
> 진자를 세우려면 "어디까지 말할지"의 결정권을 **모델에서 코드로 옮겨야** 한다.

# 7. 장점 — 지금 형태가 잘하는 것

## 7-1. 유형별로 검색 전략이 다르다

이게 가장 큰 강점이다. 대부분의 RAG는 "질문 → 벡터 검색 → LLM" 하나로 끝낸다.
우리는 질문의 성격에 따라 **찾는 방법 자체를 바꾼다.**

| 유형 | 전략 | 왜 |
|---|---|---|
| ①② | 벡터 검색 | 어느 문서인지 모르니 의미로 찾는다 |
| ③ | 기업별 분리 검색 | 한 번에 하면 한쪽으로 쏠린다 |
| ④ | 목록 필터 직행 | "전부"가 필요하니 근사치는 안 된다 |
| ⑤ | 희소한 쪽 앵커 | 1,100 대 9면 9에서 출발한다 |
| ⑥ | 수치·배경 이원 수집 | 값과 이유가 다른 섹션에 있다 |

## 7-2. 판단을 코드로 옮겼다

기권할지, 어느 유형인지, 어느 정정본이 최신인지, 표의 어느 열이 당기인지 —
**전부 코드가 셀 수 있는 것들이라 코드가 정한다.**
결과가 결정적이고, LLM이 흔들려도 버틴다.
캐시 없이 돌려도 당시 점수(28/30)가 그대로 나온 게 그 증거다.

## 7-3. 실패가 기록으로 남아 있다

`EVAL_LOG.md`에 실험 9개가 전부 있다. **되돌린 실험과 퇴행까지.**
`PAPERS.md`에 논문 → 코드 매핑이 있고, `AUDIT.md`에 감사 결과가 있다.
같은 길을 두 번 가지 않는다.

## 7-4. 안전장치가 겹겹이다

- `redact` 삭제 상한 40% — 검증기가 답변을 비우지 못하게
- `table_consistent` 합계 검산 — 파싱 실패를 스스로 감지
- `pick_keywords` 폴백 — 거짓 부재를 만들지 않게
- `latest_version` 사이클 가드 — 무한루프 방지
- `answer_question` 최상위 try/except — 어떤 예외도 오답 1건으로 격하

# 8. 단점과 문제점 — 정직하게

## 8-1. 손으로 만든 어휘 목록이 많다 ★ 가장 큰 약점

| 목록 | 위치 | 내용 |
|---|---|---|
| `ALIAS` | extract | 현대차→현대자동차 등 6쌍 |
| `ITEM_ALIAS` | slice4 | 자사주→자기주식 등 10쌍 |
| `FUNDING_KEYWORDS` | slice4 | 자금조달 수단 5종 |
| `AGG_WORDS` | slice4 | 합계·차이·비교 등 13개 |
| `ANNUAL_HINT` | slice6 | 매출구성·비중 등 6개 |
| `CAUSE_HINT` | slice6 | 때문·따라·인해 등 15개 |
| `BG_SECTIONS`, `ANNUAL_SECTIONS` | slice6 | 섹션 이름 |
| 라우터 보정 정규식 | main | 발행·증자·사채·계약 등 |

**목록 밖 표현이 오면 안 걸린다.** 블라인드 6문항과 본선 문항에서 이게 드러날 수 있다.

완화 장치는 있다. 대부분 실패해도 **퇴행이 아니라 미적용**으로 끝나게 만들어 뒀다
(`pick_keywords`는 필터를 안 걸고, `annual_wanted`는 표 주입을 안 하고 기존 경로로 돌아간다).
그래도 **점수를 못 얻는다는 사실은 같다.**

## 8-2. 최종 생성 호출이 여전히 비결정적이다

슬롯 캐시로 extract는 고정했지만 **답변 생성은 못 고정한다.**
T6-O-005가 같은 근거로 회차마다 2024년 매출을 7.4조 / 10.77조 / 12.4조로 다르게 읽는다.

**이건 우리가 통제할 수 없는 영역**이고, 평가에서 운에 좌우되는 문항이 남는다는 뜻이다.

## 8-3. 라우터 보정이 규칙 나열이다

지금 6개 규칙이 `elif` 사슬로 쌓여 있다. 규칙이 더 늘면:
- 순서 의존성이 생긴다(앞 규칙이 걸리면 뒤는 안 본다)
- 규칙끼리 충돌할 수 있다
- 어느 규칙이 발동했는지 추적이 어려워진다

지금은 `trace`에 남기고 있지만 규칙이 10개를 넘으면 관리가 어려워진다.

## 8-4. 검증기가 경고만 하고 아무것도 막지 않는다

`check_grounding`·`check_hedging`·`check_dates`가 전부 `warn` 모드다.
**탐지는 하는데 답변은 그대로 나간다.** 채점에 직접 기여하지 않는다.

차단으로 올리려면 오탐률을 재야 하는데, 그러려면 문장 단위 골드 라벨이 필요하다
(사람이 100~150건을 손으로 라벨링). 아직 안 했다.

## 8-5. 성능 — 메모리와 지연

**메모리**: 경량 색인으로 11.3GB → 5.8GB로 줄였지만,
배포 서버(4GB)에서 실제로 도는지는 **아직 검증 못 했다.**
로컬에 다이어트 산출물(`server/artifacts/`)이 없어 확인이 불가능했다.

**지연**: 최대 16초. 유형④⑥이 근거를 많이 넣어서 느리다.
평가에 응답 속도가 반영될 가능성이 있다.

**시작 시간**: 경량 색인을 처음 만들 때 chunk_meta.jsonl 1GB를 파싱한다(약 40초).
pickle 캐시가 있어 두 번째부터는 빠르지만, **배포 시 첫 기동이 느리다.**

## 8-6. 유형③은 문항이 3개뿐이라 통계가 약하다

T3-C-002(별도/연결 혼동)는 실험 10에서 해결했다. 원인은 두 가지가 겹친 것이었다.
`FIN_SEC` 목록의 띄어쓰기 불일치, 그리고 두 스코프를 한 표에 병기한 요약표를
연결 밀도 규칙이 걸러내던 것. 자세한 것은 `EVAL_LOG.md` 실험 10에 있다.

남은 약점은 정확도가 아니라 **표본 크기**다. 유형③은 문항이 3개라 한 문항이
0.33점을 움직인다. 이 구간 점수는 신뢰구간이 넓다고 보고 말해야 한다.

## 8-7. 코드가 slice1에 몰려 있다

408줄. 유형①② 로직 + 검색기 생성 + 경량 색인 + 공통 유틸(`year_of`, `chain_years`,
`find_path`, `with_text`)이 다 여기 있다. 다른 slice가 전부 여기서 import한다.

**바꾸면 파급이 크다.** 지금은 잘 돌지만 구조적으로는 좋지 않다.

## 8-8. 아직 안 쓴 논문 처방들

`PAPERS.md`의 적용 대기 목록:
- **ACORN 사전 필터** — 사후 필터는 선택도 0.1%에서 구조적으로 붕괴한다. 명섭 형 몫
- **하이브리드 BM25 + 리랭커** — 금융 코퍼스에서 Recall@5 +26.7% 보고. 명섭 형 몫
- **표 행 단위 색인** — 검색 실패의 73%가 표 구조. 명섭 형 몫
- **Self-Ask 분해 호출** — 개수 계약으로 대체됨. 실패하면 격상
- **FinGround 수치 검증** — 날짜만 구현. 금액은 단위 변환 때문에 보류

# 9. 개선 후보 — 어디를 어떻게 건드릴 수 있나

여기부터가 네가 판단할 부분이다. 각각 어디를 고치는지와 예상 효과를 적었다.

## 9-1. 남은 실패 2문 (직접적)

**T3-C-002 별도/연결** — `scope_backfill`이 뽑는 후보 순서를 바꾸거나,
"당기순이익"처럼 항목명이 명확할 때 그 항목이 든 행만 추출해 확정치로 주입
(slice6의 `current_period_table` 방식을 재무제표에 적용).

**T6-O-005 생성 흔들림** — 수주잔고 표를 코드가 직접 뽑아 주입하면
'34,495,064'를 확정으로 넣을 수 있다. 지금은 검색에 맡기고 있다.

## 9-2. 어휘 목록 의존 줄이기 (일반화)

가장 값어치 있는 방향이다. 블라인드·본선에 직결된다.

- `ITEM_ALIAS`를 코퍼스에서 자동 생성 — 보고서명에 실제로 등장하는 어휘를 모아 사전을 만든다
- 라우터 보정을 규칙 나열에서 **판정 함수**로 정리 — 조건을 명시적으로 분리해 순서 의존을 없앤다
- `CAUSE_HINT`·`ANNUAL_HINT`를 임베딩 유사도로 대체 — 목록 대신 의미로 판정

## 9-3. 검증기를 차단으로 승격 (품질)

`check_grounding`을 `cut` 모드로 올리려면 오탐률 측정이 선행이다.
평가셋 30문항의 답변을 문장 단위로 라벨링하면 된다(한 시간 정도).
효과가 있으면 환각방지 지표에서 점수를 얻는다.

## 9-4. 성능 (배포 직결)

- 다이어트 산출물을 빌드해서 4GB에서 실제로 도는지 확인 ← **가장 급하다**
- 경량 색인을 SQLite로 바꿔 첫 기동 시간 단축
- 유형④⑥의 컨텍스트 예산을 줄여 지연 개선(정확도 손실 측정 필요)

## 9-5. 구조 (유지보수)

- slice1의 공통 부품(`year_of`·`chain_years`·`find_path`·`with_text`·`SLIM`)을
  `common.py`로 분리 — 지금은 slice1을 고치면 전부가 영향받는다
- 부재 응답을 공통 함수로 — 지금 5개 파일에 문구가 제각각이다

## 9-6. 팀에 요청할 것

- **명섭 형**: 표 행 단위 색인(검색 실패의 73%), 사명 별칭 처리, 하이브리드 검색
- **경욱 형**: 다이어트 켜진 상태에서 우리 모듈 동작 확인, blind 6문 결과 공유
