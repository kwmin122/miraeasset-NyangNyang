# Fable × Sonnet 운영 규칙

토큰 절약을 위해 **비싼 판단은 Fable, 손이 많이 가는 구현은 Sonnet**으로 분리한다.
목표는 속도가 아니라 **속도와 정확도의 균형** — 이 프로젝트는 골드 하나 틀리면 평가셋 전체가 오염된다.

## 1. 역할

| | Fable (계획·검증) | Sonnet (구현) |
|---|---|---|
| 하는 일 | Brief 작성, 역설명 승인, 완료 검수, **질의셋 골드 최종 확정** | 코드 작성, 테스트 실행, 후보 발굴, 측정, 보고 |
| 호출 시점 | 슬라이스당 2~3회: ①Brief ②역설명 승인 ③완료 검수 | 슬라이스 진행 전체 |
| 읽는 것 | `docs/LOG.md` 최신 항목 + git diff | `CLAUDE.md` + `docs/SLICES.md`의 해당 Brief (전체 히스토리 불필요) |

## 2. 슬라이스 루프

```
Fable: Brief 작성 (SLICES.md에 기록)
  → Sonnet: 역설명 출력 (코드 만지기 전)
  → 사용자/Fable: 승인
  → Sonnet: 구현 + 자체 테스트
  → Sonnet: 완료 보고 (LOG.md에 append)
  → Fable: 독립 검수 → 통과 시 슬라이스 완료 표시
```

## 3. 역설명 (Sonnet, 구현 착수 전 필수)

Brief를 읽고 **자기 말로** 5~8줄:

- 무엇을 만드는가 / 왜 (사용자에게 뭐가 좋아지나)
- 입출력·완료 기준 (Brief와 다르게 이해했으면 여기서 드러나야 함)
- 건드릴 파일 / **건드리지 않을 파일**
- 예상 함정 1개 이상

역설명이 Brief와 어긋나면 사용자는 승인하지 말고 Fable에게 넘긴다.

## 4. 완료 보고 (Sonnet, LOG.md에 append)

- 무엇을 했나 (변경 파일 목록)
- **실행한 검증 명령과 출력 원문** (요약 금지 — 숫자·에러 그대로)
- Brief에서 벗어난 것 (없으면 "없음"이라고 명시)
- 남은 것 / 확신 없는 부분

## 5. Sonnet 중단 조건 (즉시 멈추고 갈등 보고)

1. 정본(SPEC/Brief)과 코드 현실이 불일치
2. `/answer` 응답 스키마를 바꿔야 할 것 같을 때
3. `data/` 하위 파일을 수정해야 할 것 같을 때
4. Brief 범위 밖 작업이 필요해 보일 때 (몰래 추가 금지)
5. 완료 기준을 달성할 수 없다고 판단될 때

**갈등 보고 형식**: 무엇이 충돌하나 / 근거 (파일:줄, 실행 결과 원문) / 선택지 A·B + 추천 1개.
실패도 산출물이다 — 정직한 실패 리포트가 어설픈 성공 선언보다 낫다.

## 6. Fable 독립 검수 (4층)

Sonnet의 보고를 믿지 않고 직접 확인한다:

1. **기능**: 완료 보고의 검증 명령을 직접 재실행
2. **명세**: Brief 완료 기준을 한 줄씩 대조
3. **재현**: 클린 상태(서버 재기동 등)에서 한 번 더
4. **품질**: 절대 규칙(CLAUDE.md) 위반·불필요한 변경(diff에 범위 밖 파일) 여부

## 7. 5대 하드룰

1. 독립 검증 없이 "완료" 선언 금지 — 됐다는 보고 ≠ 됐다
2. 역설명 없이 구현 착수 금지
3. 승인 없는 기능 추가 금지 (좋아 보여도)
4. 충돌·이상 징후는 숨기지 말고 표면화
5. 완료의 정의 = "코드가 존재한다"가 아니라 "요구 품질로 재현된다"
