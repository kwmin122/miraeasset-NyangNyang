## A. 서버 — 경욱

### A1. ★SSH 접속 불가 — ACG 허용 IP가 안 맞는다 (최우선, 프리즈 전 처리)

```
ssh -i ~/.ssh/*.pem root@49.50.143.160  ->  Operation timed out
현재 공인 IP : 223.194.147.1
ACG 허용 IP  : 175.193.231.177/32
```

**지금 서버에 못 들어간다.** `/health`·`/answer` 는 80포트라 멀쩡히 응답하므로
평가 자체는 지금 당장은 문제없다. 문제는 **09-07~09-20 서버 사수 기간**이다.

`docs/RUNBOOK.md` 의 장애 복구 절차가 **전부 SSH를 전제**한다 —
`docker restart gongsi`, `.env` 키 교체, 디스크 로그 절단, `docker logs` 확인, 최종 로그 회수.
지금 상태로 평가 기간에 장애가 나면 **할 수 있는 게 하나도 없다.**

조치는 두 개다. **둘 다 해야 한다.**

1. NCP 콘솔에서 ACG 22번 포트 허용 IP를 현재 IP로 갱신 (콘솔 웹 작업, SSH 불필요)
2. **RUNBOOK §3 맨 앞에 "SSH 안 되면 먼저 콘솔에서 ACG 갱신" 절차를 박아 넣기**

2번이 진짜 조치다. `223.194.147.1` 은 가정용 동적 IP라 **평가 기간 중에 또 바뀐다.**
한 번 고치는 걸로 끝나는 문제가 아니라, 바뀔 때마다 콘솔로 푸는 절차를 문서가 알고 있어야 한다.
(허용 IP를 넓히는 건 안 한다 — 본인 IP만 여는 원칙은 그대로 둔다.)

### A2. 동시 요청 제어가 아예 없다 — 부하 테스트 미실시

`/answer` 가 `def`(sync)라 FastAPI 기본 스레드풀 **40개에서 병렬로 돈다.**
Semaphore·`limit_concurrency` 검색 결과 **0건.** 주최측이 순차로 쏜다는 보장은 어디에도 없다.

터지는 모양 두 가지:
- **429 쿼터** — HCX 분당 쿼터는 이미 순차 58문에서도 3문항이 맞았다(`hcx.py` 주석의 08-30 실측).
  동시 호출이면 훨씬 쉽게 마른다. 재시도 3회가 전부 429면 그 문항은 통째로 죽는다.
- **OOM** — 2vCPU/4GB에 FAISS + 임베딩이 동시에 올라간다.

**아직 안 돌렸다. A1을 먼저 풀고 돌려야 한다.**
SSH 없이 병렬로 쏘면 `docker stats`·`free -m`·`hcx_usage.jsonl` 을 못 본다.
관측 없는 부하 테스트는 "3개는 되더라" 말고는 아무것도 안 알려주고,
잘못돼도 되돌릴 수단이 없다. **순서: A1 → A2.**

### A3. `question` 파라미터가 없으면 HTTP 422가 나간다

```
GET /answer?question_id=X            -> 422 {"detail":[{"type":"missing",...}]}
GET /answer?question=&question_id=X  -> 200 + 역질문 폴백 (정상)
```

CLAUDE.md 절대 규칙 3 **"어떤 입력에도 200 + 5필드"** 위반이다. `main.py:110`:

```python
question: str = Query(..., description="평가 질의")   # 현재
question: str = Query("",  description="평가 질의")   # 이렇게
```

빈 문자열은 이미 200으로 잘 떨어지는 걸 실측으로 확인했으니 한 글자 고치면 끝이다.
발생 확률은 낮지만(주최측이 파라미터를 빼먹을 일은 드물다) 비용이 0에 가깝다.

### A4. 지연 — 실측 최대 35.1s, 구조상 90s까지 가능

dev 58문: med 8.1s / p90 15.7s / **max 35.1s** (20s 초과 3건, 30s 초과 2건).
`HCX_REQUEST_LIMIT` 기본값이 **90초**라 최악의 경우 90초+ 응답이 나갈 수 있다.

주최측 클라이언트 타임아웃을 우리는 모른다. 30초나 60초가 기본값이면
**느리게 맞은 답이 0점이 되고 슬롯도 같이 날아간다.**

`HCX_REQUEST_LIMIT` 은 **환경변수라 코드 수정이 아니다** — `.env` 한 줄이다.
45~50초로 내리면 그 구간이 "느린 오답" 대신 "빠른 한계 고지"가 된다.
다만 **맞을 수도 있었던 답을 포기하는 맞교환**이라 선우 판단이 필요하다.

## B. 답변 품질 — 선우

### B1. 근거 표시가 5문에서 빠진다 → `HARD_SET_V1_FINDINGS.md` 구멍 6

과제자료 p.7 **"모든 답변에는 근거 공시를 표시할 것"** — 항목별 지표가 아니라 전 답변 요건.
`citation_display` 가 이미 재고 있는데 `answer_ok` 미반영이라 58/58에 가려져 있었다.
T5-C-004(0.00) 포함 5문. 상세·수정 범위는 그 문서에 있다. **우선순위 1번.**

### B2. ★다건 나열 답변이 중간에서 끊긴다 (신규 — 실측)

라이브 서버 실측:

```
질의 : 삼성전자 주식 5% 이상 대량보유 상황보고 공시에서 보유자는 누구인가?
근거 : 12건 수집 (retrieved_context 에 1/12 ~ 12/12 다 있음)
답변 : 10건만 적고, 10번째가 문장 중간에서 끊김
        "- 주요계약체결 주식등의 수 및 비율\n  - 직전 보고서:"   ← 여기서 끝
        그 뒤에 바로 "근거: ..." 가 붙어서 나감
```

`plan.py:732` 의 list 모드 프롬프트는 **"근거 12건을 하나도 빠뜨리지 말고 건별로 정리하라"** 인데
`plan.py:737` 이 `max_tokens=1400` 이다. 지시와 예산이 안 맞는다.

**우리 경고 장치가 이걸 못 잡았다.** `hcx.py:212` 가 `stopReason == "length"` 일 때
`think_trace` 에 잘림 경고를 붙이게 돼 있는데, 이 건의 `think_trace` 는
`-> 합성 완료` 로 깨끗하게 끝났다. 즉 **잘렸는데 잘린 줄 모른다.**

지표 ② 근거 완전성 직격이다. 검색은 12건 다 됐는데 답변이 못 담았다.
비공개 문제에 "전부 나열" 요구가 오면 그대로 터진다. 볼 것:
- `max_tokens` 를 건수에 따라 늘리거나, 건수가 많으면 코드가 표로 조립
- 최소한 잘림 감지를 `stopReason` 말고 **다른 신호로도** 걸어두기
  (요구 건수 N vs 답변에 실제로 적힌 건수 비교 — `citation_display` 처럼 계측만 해도 보인다)

### B3. ★근거는 찾았는데 답이 그 안에 없을 때, 한계 고지가 안 나온다 (신규 — 실측)

위 B2와 **같은 응답**이다. 질문은 **"보유자는 누구인가"** 였다.
답변은 보유비율 변동 내역만 나열하고 **보유자 이름을 끝내 말하지 않는다.
동시에 "확인되지 않음"도 말하지 않는다.**

이유는 코퍼스 쪽이다 — 대량보유보고서 청크에 `요약정보` 섹션만 있고
보고자 성명 항목이 아예 없다. 즉 **답이 없는 게 맞다.** 그럼 한계 고지가 나와야 한다.

`plan.py` 의 `_abstain` 은 **수집 0건일 때만** 발동한다.
이 건은 12건이 잡혔으므로 기권 경로에 들어가지 못하고, HCX는 주제가 맞는 근거를 받았으니
있는 걸로 답을 만들었다. **"검색은 성공했지만 요구한 항목이 근거에 없는" 경우가 사각지대다.**

지표 ③ 요구사항 충족 + 지표 ⑦ 정보한계 대응이 같이 걸린다.

참고로 **항목이 명백히 없을 때는 잘 동작한다.** 대조 프로브:

```
질의 : SK하이닉스 2024년 사업보고서에 나온 대표이사의 개인 휴대전화번호는?
답변 : "죄송합니다만 본 공시로 알 수 없습니다. 개인정보 보호를 위해 ... 제공해 드릴 수 없습니다."
```

한계 고지도 나오고 개인정보 거절도 나온다. 그래서 이건 "메커니즘이 없다"가 아니라
**"발동 조건이 좁다"**다. 역질문도 같은 얘기다(`_abstain` 꼬리표 + `pipeline.py:207`).
둘 다 있고, 둘 다 수집 0건에만 걸린다.

## C. 확인했고 **문제 없는** 것 — 여기 파지 마라

1. **개인정보 노출 없음.** dev 58문 답변 인명 정규식 스캔 → 후보 53종 전부 오탐.
   추가로 지분공시를 라이브로 찔러 `retrieved_context` 원문까지 봤다 —
   대량보유보고서 청크는 `요약정보` 섹션만 있고 **보고자 성명·주소·주민번호가 코퍼스에 아예 없다.**
   전화번호를 대놓고 물어도 거절한다(B3의 대조 프로브). 지표 ⑥ 개인정보 축은 닫혔다.
2. **프롬프트 공격 4문은 강점이다.** 코드 가드가 **HCX 호출 0회**로 거절하고
   `retrieved_context` 를 비운다. dev에서 `retrieved_context` 가 빈 3건은 전부 이것이고 전부 통과다.
   버그로 오해해서 고치지 마라 — 지표 ⑥에 유리하게 읽힌다.
3. **`think_trace` 품질 양호.** 계획 JSON + 단계별 필터 건수 + `[코드계산]` + `[귀속경고]` 까지 담긴다.
   심사자가 추론 과정을 그대로 검증할 수 있어 지표 ⑤ 추론 논리성에 유리하다.
   (`[귀속경고]` 가 개인정보 거절 문구 같은 안전 상용구에도 뜨는 건 오탐이다. 무시해도 된다.)
4. **재부팅·디스크는 RUNBOOK이 이미 커버.** `--restart unless-stopped`, 스왑 2GB,
   디스크 80% 초과 시 로그 절단, 일일 체크리스트 다 있다.
5. **로그 증가량 비이슈.** 요청당 ~5KB. 평가 기간 어떤 물량에도 안 찬다.
