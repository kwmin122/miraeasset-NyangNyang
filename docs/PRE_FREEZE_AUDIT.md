2. **프롬프트 공격 4문은 강점이다.** 코드 가드가 **HCX 호출 0회**로 거절하고
   `retrieved_context` 를 비운다. dev에서 `retrieved_context` 가 빈 3건은 전부 이것이고 전부 통과다.
   버그로 오해해서 고치지 마라 — 지표 ⑥에 유리하게 읽힌다.
3. **`think_trace` 품질 양호.** 계획 JSON + 단계별 필터 건수 + `[코드계산]` + `[귀속경고]` 까지 담긴다.
   심사자가 추론 과정을 그대로 검증할 수 있어 지표 ⑤ 추론 논리성에 유리하다.
   (`[귀속경고]` 가 개인정보 거절 문구 같은 안전 상용구에도 뜨는 건 오탐이다. 무시해도 된다.)
4. **재부팅·디스크 절차는 RUNBOOK이 커버.** `--restart unless-stopped`, 스왑 2GB,
   디스크 80% 초과 시 로그 절단, 일일 체크리스트 다 있다.
   (**단 장애 *탐지* 명령은 죽어 있었다 — A7. 09-03에 고쳤다.**)
5. **로그 증가량 비이슈.** 요청당 ~5KB. 평가 기간 어떤 물량에도 안 찬다.
6. **서버 자원은 걱정 안 해도 된다 (09-03 실측).** 부하를 걸어놓고 잰 값이다:
   ```
   디스크        30G 중 16G 사용 (56%)
   메모리        부하 중 1.96GiB / 3.32GiB 평탄 (스왑 29MB -> 270MB, 여유 2GB)
   CPU           최대 54.68%
   재시작 횟수   0회 (Up 24h, --restart unless-stopped)
   에러 로그     최근 48시간 0건
   ```
   OOM·디스크·재시작 축은 파지 마라. **A2에서 확인했듯 병목은 전부 HCX 쿼터 쪽이다.**
7. **요청 1건당 HCX 호출은 2회다** (계획 `plan.py:100`, 합성 `plan.py:737`).
   팬아웃 병렬 호출은 없다 — `hcx.py:146` 의 `threading.Thread` 는 단일 호출 벽시계 감시견이다.
   분당 호출량을 계산할 때 이 2배수를 쓰면 된다.

### ⚠ A4 와 B2 는 서로 반대로 당긴다 — 순서를 지켜라
